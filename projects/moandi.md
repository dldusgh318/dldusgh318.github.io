## 어떤 프로젝트인가요

시술 모델이 필요한 디자이너와 모델을 연결하는 매칭 플랫폼입니다. 신촌연합 IT창업 학회 CEOS에서 기획·디자인·FE·BE 각 2명으로 팀을 꾸렸고, 백엔드 리드를 맡았습니다. 최종적으로 약 101개의 API가 나온 서비스입니다.

## 핵심 문제 해결

### 정렬 기준별 커서 조회를 검증하고, 중복 저장은 적용 보류

후기순·거리순 조회에 정렬값과 ID를 함께 담은 복합 커서를 구현했습니다. 동점 데이터 12건으로 확인해 보니, ID만 쓴 커서는 6건을 누락했고 복합 커서는 12건을 모두 조회했습니다.

| 정렬 | Offset | Cursor |
| --- | --- | --- |
| 최신순 | 24.665ms | 0.538ms |
| 후기순 | 590.200ms | 588.004ms |

Offset과 비교한 결과, 정렬 기준에 따라 성능 차이가 달랐습니다. 별도 후기순 실험에서는 공고에 리뷰 수를 복제한 구조가 574.054ms → 0.477ms로 빨라졌습니다. 하지만 리뷰가 바뀔 때마다 여러 공고를 갱신해야 하는 부담과 정합성 복구 책임을 고려해, **서비스에는 적용을 보류**했습니다.

> 로컬 SQL 실험: MySQL 8.0.46, 합성 공고 10만 건, Page 1,000, LIMIT 21, warm buffer. 후기순 구조 변경은 리뷰 20만 건, 30회 측정, SQL p50의 별도 실험으로 기준값이 다릅니다.

### 파일 전송을 사용자와 S3 사이로 옮겨 서버 부담 감소

Spring이 파일을 받아 byte로 바꾼 뒤 다시 S3로 보내던 구조를 Presigned URL로 바꿨습니다. 서버는 권한 확인과 UUID 경로, 5분짜리 URL 발급만 맡고, 파일은 사용자가 S3로 직접 보냅니다.

| 지표 | 파일 중계 | URL 발급 |
| --- | --- | --- |
| 요청 스레드 점유 | 27.67ms | 1.06ms |
| 메모리 할당 | 15.74MB | 0.079MB |

> 5MB, 동시 요청 1개, 준비 10회·측정 30회, p50. 로컬 HTTP 수신기로 격리 비교했으며, 실제 S3 운영 성능이나 전체 업로드 시간과는 다릅니다.
