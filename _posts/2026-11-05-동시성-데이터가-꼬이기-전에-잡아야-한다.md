## 서버와 동시 실행

트래픽이 많지 않아도 요청은 많이 들어올 수 있다. 따라서 서비스의 규모가 어떻든, 우리는 동시 처리를 고려해야 한다. 만약 동시에 처리하지 않고 순차적으로 요청을 처리한다면, 처리량과 응답 시간인 성능이 나빠질 것이다.

그렇다면 동시에 어떻게 요청을 처리할까? 방식은 크게 2가지가 있다.

1. **클라이언트 요청마다 스레드를 할당해서 처리**
   → 여러 스레드가 동시에 코드를 실행한다. 이때, 요청을 처리할 때 사용할 스레드 개수에 제한을 두기도 한다.
2. **비동기 IO를 사용해서 처리**
   → IO 요청을 처리할 때도 단일 스레드보다는 여러 스레드를 사용할 때가 많다.

이때 고려해야 할 점이 있다. 서로 다른 두 스레드가 동시에 같은 데이터를 조회하거나 수정하면, 문제가 없을까?

```java
public class Increaser {
    private int count;

    public void inc() {
        count = count + 1;
    }

    public int getCount() {
        return count;
    }
}
```

```java
Increaser increaser = new Increaser();
Thread[] threads = new Thread[100];

// 동시에 100개의 스레드 생성 후 메서드 진행
for (int i = 0; i < 100; i++) {
    Thread t = new Thread(() -> {
        for (int j = 0; j < 100; j++) {
            increaser.inc();
        }
    });
    threads[i] = t;
    t.start();
}

for (Thread t : threads) {
    t.join();
}

System.out.println(increaser.getCount());
```

이 코드를 여러 번 실행하다 보면, 기댓값인 10000이 아닌 잘못된 값을 출력할 때도 있다. 대체 왜일까?

→ 여러 스레드가 동시에 `count = count + 1` 코드를 진행하면서 데이터에 오류가 생기기 때문이다.

이런 동시성 문제는 처음부터 잘 보이지 않기에, 우린 늘 고려하면서 개발해야 한다. 앞으로 알아보자.

> **💡 경쟁 상태**
> 여러 스레드가 동시에 공유 자원(ex. 위의 코드에서의 `count`)에 접근할 때, 접근 순서에 따라 결과가 달라지는 상황
{: .prompt-tip }

## 프로세스 수준에서의 동시 접근 제어

### 잠금(lock)을 이용한 접근 제어

잠금을 사용하면 공유 자원에 접근하는 스레드를 한 번에 하나로 제한할 수 있다.

```text
1. 잠금을 획득
2. 공유 자원에 접근
   (임계 영역: 동시에 둘 이상의 스레드나 프로세스가 접근하면 안 되는 공유 자원에 접근하는 코드 영역)
3. 사용 후 잠금을 해제
```

lock은 한 번에 한 스레드만 획득하며, 획득하지 못한 스레드들은 잠금이 해제될 때까지 대기한다. 사용이 끝나면 잠금이 해제되고, 대기하던 스레드 중 하나가 잠금을 획득해 자원에 접근하며 이 과정을 반복한다.

자바에서는 `ReentrantLock`을 사용해 접근 제어를 할 수 있다. 우리가 흔히 알고 있는 `synchronized`보다 더 유연하고 확장된 기능을 제공한다.

```java
import java.util.concurrent.locks.ReentrantLock;

class Example {
    private final ReentrantLock lock = new ReentrantLock(); // 락 객체 생성

    public void accessResource() {
        lock.lock(); // 락 획득
        try {
            // 임계 영역 (Critical Section) - 공유 자원 작업 수행
        } finally {
            lock.unlock(); // 예외 발생 여부와 상관없이 락 해제
        }
    }
}
```

| 구분 | `synchronized` | `ReentrantLock` |
| --- | --- | --- |
| **방식** | 암묵적 (JVM이 자동 관리) | 명시적 (`lock()` / `unlock()` 직접 호출) |
| **해제** | 블록을 벗어나면 자동 해제 | `unlock()`을 직접 호출해 해제 |
| **대기 시간 설정** | 불가능 (무한정 대기) | `tryLock(timeout)` 사용 가능 |
| **공정성 설정** | 불가능 (비공정만 지원) | 생성자로 공정/비공정 선택 가능 |
| **인터럽트 처리** | 대기 중단 불가능 | `lockInterruptibly()` 지원 |

### 동시 접근 제어를 위한 구성 요소

앞에서 본 `ReentrantLock`은 한 번에 1개 스레드만 잠금을 구할 수 있어서, 나머지 스레드는 잠금이 해제될 때까지 대기해야 한다. 그렇다면 다른 방법들은 뭐가 있을까?

#### 1. 세마포어

동시에 실행할 수 있는 스레드 수를 제한한다. 각 스레드는 세마포어에서 퍼밋을 획득한 뒤에 코드 실행이 가능하며, 퍼밋이 0인 상태에서 다른 스레드들은 반환될 때까지 대기해야 한다.

```text
1. 세마포어에서 퍼밋 획득 (허용 가능 숫자 1 감소)
2. 코드 실행
3. 세마포어에서 퍼밋 반환 (허용 가능 숫자 1 증가)
```

```java
import java.util.concurrent.Semaphore;

class Example {
    // 동시에 실행할 수 있는 스레드 수를 5개로 제한
    private final Semaphore semaphore = new Semaphore(5);

    public String accessResource() {
        try {
            semaphore.acquire();
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
        try {
            String data = ...;
            return data;
        } finally {
            semaphore.release(); // 퍼밋 반환
        }
    }
}
```

여기서 두 번째 try 문의 코드는 동시에 최대 5개의 스레드까지만 실행할 수 있다.

#### 2. 원자적 타입

```java
public class Increaser {
    private Lock lock = new ReentrantLock();
    private int count = 0;

    public void inc() {
        lock.lock();
        try {
            count = count + 1;
        } finally {
            lock.unlock();
        }
    }
}
```

위의 코드는 앞서 배운 `ReentrantLock`을 이용해 동시성 문제를 해결한 코드다. 하지만 이 방식은 CPU 효율이 떨어진다는 단점이 있는데, 그렇다면 다른 방법은 뭐가 있을까?

→ 원자적 타입을 이용하자.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Increaser {
    private AtomicInteger count = new AtomicInteger(0);

    public void inc() {
        count.incrementAndGet(); // 다중 스레드 문제없이 값을 1 증가시킴
    }

    public int getCount() {
        return count.get();
    }
}
```

해당 타입을 사용하면 다중 스레드 환경에서도 동시성 문제없이 여러 스레드가 공유하는 데이터를 변경할 수 있다.

- **원자성(Atomicity) 보장:** 멀티스레드 환경에서 락이나 `synchronized` 키워드 없이도 데이터 조작 연산이 도중에 끊기지 않고 단 하나의 단위(Atomic)로 실행되도록 보장한다.
- **CAS(Compare-And-Swap) 알고리즘 사용:** 하드웨어 수준에서 제공하는 atomic 지시어를 활용해 락을 걸지 않고도(Non-blocking) 안전하고 빠르게 동시성 문제를 해결한다.

### 동시성 지원 컬렉션

자바의 `HashMap`이나 `HashSet`처럼 스레드에 안전하지 않은 컬렉션을 여러 스레드가 공유하면 동시성 문제가 발생할 수 있다.

→ sol. 동기화된 컬렉션을 사용하자. (데이터를 변경하는 모든 연산에 잠금을 적용하자)

```java
Map<String, String> map = new HashMap<>();
// 동기화된 컬렉션 객체 생성
Map<String, String> syncMap = Collections.synchronizedMap(map);
syncMap.put("key1", "value1"); // put 메서드는 내부적으로 synchronized로 처리됨
```

자바의 `Collections`는 동기화된 컬렉션을 생성하는 메서드를 제공하는데, 이를 사용하면 기존 컬렉션 객체를 동기화된 컬렉션 객체로 변환할 수 있다.

→ 변경이나 조회와 관련된 메서드가 모두 동기화된 블록에서 실행된다.

`Collections` 말고도 `ConcurrentHashMap` 등이 있다.

## DB와 동시성

우리는 DB의 트랜잭션 기능 덕에 다양한 동시성 문제를 해결할 수 있으나, 모든 문제를 해결할 수는 없다.

앞에서는 프로세스 수준에서 잠금을 사용했다면, 이젠 DB에 맞는 잠금 기능을 알아보자.

### 비관적 락

데이터에 먼저 접근한 트랜잭션이 잠금을 획득하는 방식으로, 쿼리는 다음과 같은 형태다. (MySQL 기준)

```sql
select * from 테이블 where 조건
for update
```

조건에 해당하는 레코드를 조회하면서 동시에 잠금을 획득한다. 만약 한 트랜잭션이 특정 레코드에 대한 잠금을 획득하면, 다른 트랜잭션들은 잠금이 해제될 때까지 대기해야 한다.

✅ 레코드에 대한 잠금은 트랜잭션이 종료될 때 (COMMIT or ROLLBACK) 반환된다.

![비관적 락](ch6-2-pessimistic.png)

> **💡 분산 잠금**
> 여러 프로세스가 동시에 동일한 자원에 접근하지 못하도록 막는 방법. 분산 환경에서 유용하다.
> 트래픽이 많을 때엔 Redis를 이용해 분산 잠금을 구현할 수 있다.
{: .prompt-tip }

### 낙관적 락

낙관적 락은 잠금을 사용하진 않으나, 데이터를 조회한 시점의 값과 수정하려는 시점의 값이 같은지 비교하는 방식으로 동시성 문제를 처리한다. 대기 과정이 없으니, 비관적 락보다 빠른 응답이 가능하다.

동작 방식은 다음과 같다.

1. SELECT 쿼리를 실행할 때 version 칼럼을 함께 조회한다.

   ```sql
   select ..., version from 테이블 where id = 아이디
   ```

2. 로직을 수행한다.
3. UPDATE 쿼리를 실행할 때 version 칼럼을 1 증가시킨다. 이때 version 칼럼 값이 1에서 조회한 값과 같은지 비교하는 조건을 where 절에 추가한다.

   ```sql
   UPDATE 테이블 SET ..., version = version + 1
   WHERE id = 아이디 AND version = [1에서 조회한 version 값]
   ```

4. UPDATE 결과로 변경된 행 개수가 0이면, 이미 다른 트랜잭션이 version 값을 증가시킨 것이므로 데이터 변경에 실패한 것이다. 이 경우 트랜잭션을 롤백한다.
5. UPDATE 결과로 변경된 행 개수가 0보다 크면, 다른 트랜잭션보다 먼저 데이터 변경에 성공한 것이므로 트랜잭션을 커밋한다.

### 외부 연동과 잠금

만약 트랜잭션 범위 내에서 외부 시스템과 연동해야 한다면, 낙관적 락보다는 비관적 락을 고려하는 게 좋다.

ex) 주문 취소 과정에서 외부 PG 시스템을 호출해 결제까지 취소해야 하는 상황

![외부 연동과 낙관적 락](ch6-3-external-optimistic.png)

낙관적 락을 사용하면 결제는 이미 취소됐는데 데이터 변경에 실패해서 트랜잭션이 롤백될 수도 있다.

### 증분 쿼리

```java
// 주제 조회
Subject subject = jdbcTemplate.queryForObject(
    "select id, joinCount, ... from SUBJECT where id = ?", 매퍼코드, id
);

// 참여 데이터 추가
joinToSubject(joinData, subject); // SUBJECT_JOIN 테이블에 추가

// 주제 데이터의 참여자 수 증가
jdbcTemplate.update(
    "update SUBJECT set joinCount = ? where id = ?",
    subject.getJoinCount() + 1, subject.getId()
);
```

이 코드의 문제점은 뭘까? 만약 동시에 두 명이 이 코드를 실행하면, 참여자 수가 2가 아닌 1만 증가할 수도 있다. 물론 비관적 락으로 해결할 수 있지만, 응답 시간까지 고려한다면 **증분 쿼리**를 사용하는 방법이 있다.

```sql
update SUBJECT set joinCount = joinCount + 1 where id = ?
```

이렇게 하면 DB가 원자적 연산을 순차적으로 실행하기에, 데이터가 누락되지 않는다. 다만 DB에 따라 다를 수도 있으니 반드시 검증해 볼 것!!

## 잠금 사용 시 주의 사항

### 잠금 해제하기

획득도 중요하지만, 잠금을 해제해야 다음 스레드가 작업을 실행하므로 반드시 해제해야 한다.

```java
lock.lock();
try {
    // 코드
} finally {
    lock.unlock();
}
```

### 대기 시간 지정하기

만약 임계 영역 코드 실행에 0.5초가 걸리고, 1000개의 스레드가 락을 시도하는 상황이라면?
1000번째 스레드는 499.5초를 기다려야 코드 실행이 가능하다.

이렇게 대기 시간이 길어지면 사용자들은 결과를 모른 채 응답을 기다려야 한다. 그러니 대기 시간을 지정하거나, 바로 실패를 반환해서 응답하자.

**1. 대기 시간 제한**

```java
boolean acquired = lock.tryLock(5, TimeUnit.SECONDS); // 5초 제한
if (!acquired) {
    // 잠금 획득 실패
    throw new RuntimeException("Failed to acquire lock");
}
// 잠금 획득 성공
try {
    // 자원 접근 코드 실행
} finally {
    lock.unlock();
}
```

**2. 바로 결과 반환**

```java
boolean acquired = lock.tryLock();
if (!acquired) {
    // 잠금 획득 실패
    throw new RuntimeException("Failed to acquire lock");
}
```

### 교착 상태(deadlock) 피하기

교착 상태: 2개 이상의 스레드가 서로가 획득한 잠금을 대기하면서 무한 대기 중인 상황

![교착 상태](ch6-4-deadlock.png)

sol. 잠금 대기 시간을 제한하자.

> **💡 라이브락**
> 교착 상태는 두 스레드가 모두 아무것도 안 하고 대기 중이라면, 라이브락은 스레드나 프로세스가 계속 동작을 하고 있음에도 잠금을 획득하지 못하는 상황을 뜻한다.
> sol. 우선순위를 정해 두면 해소할 수 있다.

## 단일 스레드로 처리하기

사실, 동시성 문제는 여러 스레드가 공유 자원에 접근할 때 발생한다. 만약 단일 스레드라면 동시성 문제가 발생하지 않는다.

![단일 스레드로 처리하기](ch6-5-single-thread.png)

여기서는 상태 관리 스레드만 데이터를 조작할 수 있고, 다른 스레드는 작업 큐에 작업을 추가할 뿐 데이터 조작은 할 수 없다.

Go 언어에는 "메모리를 공유하는 방식으로 고루틴 간에 소통하지 말고, 통신을 통해 메모리를 공유하라"는 말이 있다고 한다.

![Go 채널](ch6-6-channel.png)

단일 스레드나 이러한 방식은 동시성 문제 해결은 쉽지만, 구조가 복잡해지기에 상황을 고려해서 검토해야 한다.

## 더 찾아본 것: 쿠버네티스, 도커, 테라폼은 동시성을 어떻게 다룰까?

쿠버네티스, 도커, 테라폼은 모두 Go 언어로 만들어졌다. 그럼 이들은 동시성 문제를 해결할 때 채널을 썼을까?

**규모가 큰 프로젝트일수록 락(뮤텍스)을 더 많이 쓴다고 한다.**

### 논문: 실제 Go 프로젝트의 동시성 버그 연구 (ASPLOS 2019)

연구진이 도커, 쿠버네티스, etcd, CockroachDB, BoltDB, gRPC 이렇게 실제 Go 소프트웨어 6개를 골라서 동시성 버그를 분석했다.

**① 이 프로젝트들도 락을 채널보다 더 많이 쓴다!**

Go 프로그램에서 전통적인 lock/unlock 방식의 공유 메모리 동기화가 여전히 더 높은 비중을 차지했다.

**② 채널이 버그를 더 많이 만든다?**

프로그램이 멈춰 버리는 버그 중 약 42%는 공유 메모리 보호 실수, 58%는 메시지 전달(채널) 실수였다. 락이 채널보다 훨씬 많이 쓰이는데도 이 비율이니까, **채널 연산 하나하나가 오히려 더 버그를 내기 쉽다고 볼 수 있다.**

반대로 데이터가 꼬이는 버그는 약 80%가 공유 메모리를 제대로 안 보호해서, 20%가 채널 실수였다.

| 버그 종류 | 주된 원인 |
| --- | --- |
| 프로그램이 멈춤 (데드락 등) | **채널** 실수가 더 많음 |
| 데이터가 꼬임 (경쟁 상태) | **락** 누락이 대부분 |

**채널을 쓰면 데이터 꼬임은 줄지만 대신 멈춤 버그가 늘어나서,** 사실상 문제가 사라지는 게 아니라 종류가 바뀐다고 볼 수 있다.

### 쿠버네티스의 "진짜" 동시성 처리

쿠버네티스가 정말 큰 규모의 동시성 문제를 푸는 방식은 프로세스 안의 채널도 락도 아닌 **낙관적 락**이다.

```yaml
metadata:
  name: my-pod
  resourceVersion: "12345"   # ← 이게 version 칼럼
```

두 사람이 동시에 같은 리소스를 수정하면, 먼저 쓴 쪽이 `resourceVersion`을 올리고 나중에 쓴 쪽은 **"버전이 안 맞음(Conflict)"으로 실패**한다. 우리가 배운 낙관적 락의 `UPDATE ... WHERE version = ?`랑 완전히 똑같은 구조다.

왜 낙관적 락을 쓸까?..

쿠버네티스는 수많은 컨트롤러와 사용자가 네트워크 너머에서 같은 리소스를 건드린다. 이때 일반 락을 쓰면 누군가가 락을 잡은 상태로 컴퓨터가 멈춘다거나, 네트워크가 느려지는 등 성능 상의 문제가 생긴다. 반면 낙관적 락은 붙잡지 않으니 다른 컴퓨터가 중간에 죽어도 영향이 가지 않는다.

> `kubectl apply` 하다가 가끔 **"the object has been modified; please apply your changes to the latest version"** 이런 에러 본 적 있으면, 그게 바로 낙관적 락이 충돌을 잡은 거라고 한다.
{: .prompt-tip }

테라폼도 비슷하다. 여러 명이 동시에 `terraform apply` 하면 인프라가 꼬이니까, **state 파일에 잠금(state lock)** 을 건다. (= 분산 잠금)

| 도구 | 동시성 처리 | 책에서 배운 것 |
| --- | --- | --- |
| 쿠버네티스 | `resourceVersion` 비교 | **낙관적 락** |
| 테라폼 | state 잠금 | **분산 잠금** |
| 코드 내부 | 뮤텍스 > 채널 | **잠금** |
