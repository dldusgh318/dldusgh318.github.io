## "서버 안 돌아가요..."

서비스를 운영하다가 이런 연락을 받아 본 적 있나요?

> "서버가 안 돌아가요.. 서비스 터진 것 같아요ㅜㅜ"

저는 있습니다. 급하게 서버에 접속해 로그를 뒤지고, 어디서 문제가 생겼는지 찾느라 한참 걸렸어요. **문제를 사용자가 먼저 발견했다**는 것 자체가 모니터링을 하지 않아서 생긴 일이었죠.

## 모니터링, 꼭 해야 하나요?

해야 합니다. 모니터링을 하면

1. **장애를 빨리 발견**하고
2. **원인을 파악**할 수 있고
3. 메모리 누수 같은 병목을 찾아 **성능을 최적화**할 수 있고
4. 결국 **사용자 경험이 좋아집니다.**

반대로 하지 않으면

1. 장애 발견이 늦어져 **사용자나 다른 파트에게서 먼저 연락**이 오고
2. 원인 파악이 어려워 **복구 시간이 길어지고**
3. 어디가 병목인지 모른 채 **성능 저하가 쌓이다 결국 장애**로 이어집니다.

게다가 요즘은 MSA 같은 분산 아키텍처가 늘면서 시스템이 점점 복잡해지고 있어요. 그래서 **지표, 로그, 트레이스를 수집하고 시각화**하는 일이 더 중요해졌습니다.

## Monitoring vs Observability

- **Monitoring**: CPU, 메모리, 네트워크 트래픽 같은 데이터를 수집·분석해 시스템의 성능과 동작을 파악하는 것
- **Observability**: 외부로 드러난 데이터를 통해 **시스템 내부 상태를 이해하는 능력**

쉽게 말하면 모니터링은 "**문제가 생겼다**"를 알려 주고, Observability는 "**왜 문제가 생겼는가**"를 설명해 줍니다. 장애를 실시간으로 감지·대응하고, 개발부터 운영까지 성능을 살피고, 이상 징후를 미리 잡아 보안 위협에도 대응할 수 있게 해 줘요.

### 세 가지 구성 요소

| 구분 | 목적 | 데이터 형태 | 핵심 질문 |
| --- | --- | --- | --- |
| **메트릭 (Metric)** | 상태·추세 | 시계열 숫자 | **무엇이** 문제인가? |
| **로그 (Log)** | 상세 분석 | 텍스트·이벤트 | **왜** 문제가 생겼는가? |
| **트레이스 (Trace)** | 흐름·병목 | 분산 추적 데이터 | **어디서** 느려지는가? |

- **메트릭**: CPU 사용률, 메모리 사용량, 요청 수처럼 일정 간격으로 재는 숫자
- **로그**: 언제 어떤 일이 있었는지 남긴 기록

  ```text
  2026-05-04 10:21:30.957 [http-nio-8080-exec-7] INFO  c.e.logdemo.service.OrderService - [ORDER-001] 정상 주문 처리가 완료되었습니다.
  2026-05-04 10:21:58.874 [http-nio-8080-exec-1] ERROR c.e.logdemo.service.OrderService - [ORDER-003] PG사(결제사) API 타임아웃으로 결제 실패!
  ```

- **트레이스**: 요청 하나가 시스템 안에서 어떤 경로로 흘렀는지 추적한 데이터

트레이스가 왜 필요할까요? 메트릭과 로그만으로는 못 잡는 상황이 있어요. p99 응답시간이 3초인데 로그에는 에러가 하나도 없다면? 트레이스를 보면 "DB 쿼리에서 2800ms가 걸렸구나"를 바로 알 수 있어요. 특히 MSA에서 A → B → C → D로 요청이 흘러갈 때 **어느 서비스가 병목인지** 찾는 데 유용합니다.

세 가지를 같이 보면 이렇게 됩니다.

```text
메트릭:   "응답시간이 1000ms네요"
로그:     "Database connection timeout"
트레이스: "DB 쿼리에서 800ms 소비됨"
→ 아! DB가 문제구나!
```

## 모니터링 도구

### Spring Boot Actuator

놀랍게도 Spring Boot 자체로도 모니터링을 시작할 수 있어요. **Actuator**는 애플리케이션의 상태, 메트릭, 빈 정보 등을 HTTP 엔드포인트로 노출해 주는 도구예요. 어떤 정보를 열지는 `application.yml`에서 정합니다.

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health, info, metrics, prometheus  # 꼭 필요한 것만
```

> `include: "*"`로 전부 열면 안 됩니다! `/actuator/env` 같은 엔드포인트로 서버의 민감한 정보가 그대로 노출될 수 있어요. `health`, `prometheus`처럼 필요한 것만 여세요.
{: .prompt-danger }

![Actuator 엔드포인트](actuator.png){: width="560" }

그런데 `/actuator/prometheus`에 들어가 보면 이런 텍스트가 끝없이 나와요.

```text
# HELP executor_active_threads The approximate number of threads that are actively executing tasks
# TYPE executor_active_threads gauge
executor_active_threads{name="applicationTaskExecutor"} 0.0
# HELP executor_pool_core_threads The core number of threads for the pool
# TYPE executor_pool_core_threads gauge
executor_pool_core_threads{name="applicationTaskExecutor"} 8.0
...
```

이걸 눈으로 보며 모니터링할 수는 없겠죠. 그래서 **외부 모니터링 스택**으로 저장하고 대시보드로 시각화합니다.

### 1. PLG 스택 + Prometheus

**P**romtail, **L**oki, **G**rafana의 조합에 메트릭용 Prometheus를 더한 구성이에요.

- **Promtail**: 서버의 로그 파일을 읽어 Loki로 보내는 가벼운 에이전트. 지정한 경로의 로그 파일을 지켜보다가, 새 줄이 생기면 읽어서 레이블(메타데이터)을 붙여 Loki로 전송합니다.
- **Loki**: 로그 저장소. 로그 **본문이 아니라 레이블만 인덱싱**하고 본문은 압축해 저장해서 가볍고 빠릅니다. 검색은 LogQL로 해요.
- **Grafana**: 메트릭, 로그, 트레이스를 시각화하는 대시보드. 원하는 대로 커스텀할 수 있어요.

![Grafana 대시보드 예시](grafana-dashboard-example.jpg)

> **Promtail은 지원이 종료됐어요.** 2026년 2월 28일부로 보안 업데이트만 제공되고, 공식적으로 **Grafana Alloy**로 옮기길 권장합니다. Alloy는 Promtail의 후속 에이전트로, 로그뿐 아니라 **메트릭과 트레이스까지** 수집할 수 있고 OpenTelemetry 표준을 지원해 특정 벤더에 묶이지 않아요.
{: .prompt-warning }

정리하면, Alloy(Promtail)가 로그를 모으면 Loki가 저장하고 Grafana가 대시보드로 보여 줍니다.

![PLG + Prometheus 구성](plg-flow.png)

**Prometheus**는 메트릭을 시계열로 수집·저장하는 시스템이에요. Loki와 다른 점은 **Pull 방식**이라는 것. Prometheus가 주기적으로 앱의 `/actuator/prometheus`에 찾아가 메트릭을 긁어 옵니다.

```yaml
# prometheus-config.yml
scrape_configs:
  - job_name: 'server_metric'
    metrics_path: '/actuator/prometheus'   # 이 경로에서
    static_configs:
      - targets: ['localhost:8080']         # 이 서버의 메트릭을 가져와
```

```text
/actuator/prometheus → Prometheus가 15초마다 Pull → 시계열 DB에 저장 → Grafana에서 PromQL로 시각화
```

### 2. AWS CloudWatch

AWS 리소스의 상태와 지표를 수집해 보여 주는 AWS의 모니터링 서비스예요.

- **지표 수집**: EC2, ELB, Route53, CloudFront 등 대부분의 서비스가 CPU, 네트워크, 디스크 I/O 같은 기본 지표를 제공해요. 메모리 사용량처럼 기본에 없는 건 CloudWatch Agent로 커스텀 지표를 만들 수 있고요.
- **경보(Alarm)**: 지표가 기준을 넘으면 SNS로 Lambda를 실행하거나 메일, 슬랙 알림을 보낼 수 있어요.
- **로그 수집**: 로그를 모아 직접 조회하거나 Kinesis, S3 등으로 넘길 수 있어요.
- **대시보드**: 수집한 지표와 로그로 대시보드를 구성할 수 있어요.

처리 시간이나 DB 쿼리 시간 같은 **애플리케이션 내부 지표**까지 CloudWatch로 보내고 싶다면 의존성을 추가합니다.

```groovy
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-registry-cloudwatch2'
```

### 3. ELK 스택

![ELK 스택](mon-1-elk.png)

- **Elasticsearch**: 데이터를 중앙에 저장하고 색인해 빠른 검색과 분석을 제공하는 분산 저장소. 로그뿐 아니라 검색이 필요한 데이터라면 무엇이든 담을 수 있어요.
- **Logstash**: 여러 소스에서 데이터를 모아 필터링·변환한 뒤 Elasticsearch로 보내는 파이프라인. PLG의 Promtail 역할이에요.
- **Kibana**: Elasticsearch의 데이터를 시각화하고 분석하는 대시보드.

Kibana에서는 **KQL(Kibana Query Language)**로 로그를 필터링해요.

```text
status : "error"                                   # 특정 값
status : "error" or status : "warning"             # OR 조건
@timestamp >= "2025-10-01T00:00:00" and @timestamp <= "2025-10-30T23:59:59"   # 시간 범위
message : *login failed*                           # 부분 문자열 (*는 와일드카드)
```

> **PLG vs ELK**: 복잡한 쿼리와 필터링이 필요하고 다양한 데이터 소스를 다룬다면 **ELK**, 단순한 쿼리로 충분하고 비용을 아끼고 싶다면 **PLG**.
{: .prompt-tip }

### 4. LGTM 스택

**L**oki, **G**rafana, **T**empo, **M**imir. 모두 Grafana Labs에서 만든 스택이에요. Loki와 Grafana는 앞에서 봤으니, 새로 나온 두 개만 볼게요.

![LGTM 스택](mon-3-lgtm.png)

**Tempo**는 대량의 분산 트레이스를 저장하는 백엔드로, 요청의 실제 경로와 구간별 지연을 추적해요. **traceID 중심**으로 설계돼 병목을 정확히 짚어 냅니다. 예전에는 트레이스를 Elasticsearch나 Cassandra에 저장해야 해서 관리가 어렵고 비쌌는데, Tempo는 **S3나 GCS 같은 객체 저장소**에 저장해 효율적으로 확장할 수 있어요.

<details markdown="1">
<summary>Tempo 내부 구조 더 보기</summary>

![Tempo 내부 구조](mon-2-tempo.png)

- **Distributor**: 수집기에서 받은 데이터를 traceID 기준으로 Ingester에 나눠 줘요. Consistent Hash Ring으로 트래픽을 고르게 분배합니다.
- **Ingester**: 트레이스를 블록 단위로 묶어 객체 저장소로 보내요.
- **Query Frontend**: 검색 요청을 여러 조각으로 나눠 Querier에 분배해요.
- **Querier**: Ingester나 저장소에서 traceID로 데이터를 찾아 돌려줘요.
- **Compactor**: 작은 블록을 큰 블록으로 합쳐 공간을 아끼고 검색 성능을 유지해요.
- **Metrics Generator** (선택): 트레이스로부터 메트릭을 만들어 Prometheus나 Mimir에 저장해요.

Grafana에서는 **TraceQL**로 트레이스를 검색해요.

```text
{ span.http.status_code >= 200 && span.http.status_code < 300 }
```

</details>

**Mimir**는 Prometheus의 한계였던 **고가용성과 장기 보관** 문제를 해결한 시계열 DB예요.

| 항목 | Prometheus | Mimir |
| --- | --- | --- |
| 저장소 | 로컬 디스크 | S3 등 원격 저장소 |
| 고가용성 | 제한적 | 완전 지원 |
| 확장성 | 단일 노드 | 수평 확장 |
| 멀티테넌시 | 미지원 | 지원 |

Prometheus처럼 Pull이 아니라 **Remote Write(Push)** 방식으로 메트릭을 받아요. 그리고 PromQL을 그대로 지원해서, 기존 PromQL 쿼리와 Grafana 대시보드를 **수정 없이** 옮겨 쓸 수 있습니다.

## 그래서 뭘 써야 할까?

정답인 스택은 없어요. 개인적으로는 이렇게 고르면 잘 맞을 것 같아요.

| 상황 | 추천 |
| --- | --- |
| 로그 분석이 중심 | **ELK** |
| AWS 운영 편의성이 중요 | **CloudWatch** |
| 오픈소스로 가볍게 시작 | **P(A)LG + Prometheus** |
| Observability까지 염두 | **LGTM** |

도구를 골랐다면, 이제 더 중요한 질문이 남아요. **"그래서 뭘 봐야 하는데?"** 다음 편에서는 꼭 봐야 할 지표와 알림 기준을 정하고, Alloy + Loki + Grafana + Prometheus로 직접 모니터링 환경을 만들어 봅니다.
