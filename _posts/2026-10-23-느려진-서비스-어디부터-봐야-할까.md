## 서버 개발자가 봐야 하는 시간

요청 하나를 처리하는 시간은 대략 이렇게 나뉜다.

- 로직 수행
- **DB 연동**
- **외부 API 연동**
- 응답 데이터 생성

이 중 비중이 가장 큰 건 보통 DB 연동과 외부 API 연동이다. 성능 개선은 결국 이 두 구간을 얼마나 줄이느냐의 싸움이다.

## 처리량과 응답 시간

- **처리량(TPS)**: 초당 처리한 트랜잭션 수
- **응답 시간**: 요청을 보내고 응답을 받기까지 걸린 시간

최대 TPS를 넘는 요청이 들어오면 서버는 초과분을 나중에 처리한다. 그만큼 대기 시간이 생기고 응답 시간이 늘어난다. 그래서 할 수 있는 일은 두 가지다.

1. 동시에 처리할 수 있는 요청 수를 늘린다.
2. 요청 하나의 처리 시간을 줄인다.

그 전에 먼저 해야 할 일은 **현재 서버의 TPS와 응답 시간을 아는 것**이다. 트래픽이 많은 시간대의 수치를 측정해 기준으로 삼고, 스카우터·핀포인트·뉴렐릭 같은 모니터링 도구를 활용한다.

### 트래픽이 늘면 왜 터질까

사용자가 늘면서 생기는 성능 문제는 대체로 이런 모습으로 나타난다.

- 어느 순간 모든 요청의 응답 시간이 심각하게 느려진다.
- 서버를 재시작하면 잠깐 괜찮다가 다시 느려진다.
- 트래픽이 줄어들 때까지 이 상황이 반복된다.

원인은 단순하다. 최대 TPS를 넘는 트래픽이 들어오기 때문이다. 해결의 출발점은 **처리 시간이 오래 걸리는 지점을 찾는 것**이다. 모니터링 도구의 실행 시간 추적 기능을 쓰고, 도구가 없다면 로그라도 남겨 두어야 나중에 원인을 좁힐 수 있다.

## 서버 확장: 수직과 수평

### 수직 확장 (Scale-up)

CPU, 메모리, 디스크 같은 장비 자원을 늘리는 방식이다. 빠르게 적용할 수 있어서 급한 불을 끌 때 좋다. 하지만 트래픽이 계속 늘면 결국 다시 한계에 부딪히고, 비용이 크며, 한 장비가 감당할 수 있는 용량에도 한계가 있다.

### 수평 확장 (Scale-out)

서버 대수를 늘리는 방식이다. 서버가 두 대 이상이면 앞단에 **로드밸런서**가 필요하다.

| 방식 | 예시 | 특징 |
| --- | --- | --- |
| 정적 | 라운드 로빈, IP 해시 | 정해진 규칙대로 분산. IP 해시는 같은 클라이언트가 항상 같은 서버로 간다 |
| 동적 | 최소 연결 등 | 서버의 현재 상태를 보고 분산. 세션 불일치 문제에 주의 |

다만 확장은 **병목에 맞게** 써야 한다. 외부 API가 느린 게 원인인데 서버를 늘려 봐야 해결되지 않는다.

## DB 커넥션 풀

DB를 쓸 때는 "연결 → 쿼리 실행 → 연결 종료"를 거친다. 요청마다 연결하고 끊으면 이 시간이 그대로 응답 시간에 더해지고, 트래픽이 늘수록 처리량이 떨어진다.

**커넥션 풀**은 DB 커넥션을 미리 만들어 두고 재사용하는 방식이다. 애플리케이션은 필요할 때 풀에서 꺼내 쓰고 끝나면 반납한다. Spring Boot는 기본으로 HikariCP를 쓴다.

### 1. 풀 크기

가장 중요한 설정이다. 풀 크기가 5이고 쿼리 하나가 1초 걸린다면, 동시에 6개 요청이 들어올 때 1개는 커넥션이 반납될 때까지 기다린다.

> 트래픽이 순간적으로 급증하는 패턴이라면 최소 크기를 최대 크기에 맞춰 두자. 급증하는 순간에는 커넥션을 새로 여는 시간도 병목이 된다.
{: .prompt-tip }

풀을 키우면 처리량이 늘 수 있지만 **DB 상태를 같이 봐야 한다.** DB CPU가 이미 80%에 가까운데 풀을 키우면 DB 부하만 더 커진다.

### 2. 커넥션 대기 시간

풀에 남은 커넥션이 없을 때 얼마나 기다릴지 정하는 값이다. HikariCP 기본값은 30초인데, 응답 시간이 중요한 서비스라면 0.5~3초 정도로 짧게 잡는 편이 낫다. 일시적인 에러가 나더라도 오랫동안 응답이 없는 것보다는 낫다.

### 3. 유휴 시간, 유효성 검사, 최대 유지 시간

밤새 쓰이지 않은 커넥션은 DB 쪽에서 끊길 수 있다. MySQL도 일정 시간 상호작용이 없으면 연결을 끊는다. 이렇게 끊긴 커넥션을 쓰면 에러가 난다.

- **최대 유휴 시간**: 쓰이지 않은 커넥션을 풀에 둘 최대 시간. DB의 비활성 타임아웃보다 짧게 잡으면 DB가 끊기 전에 풀에서 먼저 정리할 수 있다.
- **유효성 검사**: 커넥션이 살아 있는지 주기적으로 확인한다(예: `SELECT 1`).
- **최대 유지 시간**: 유효하더라도 이 시간이 지나면 닫고 새로 만든다.

> 최대 유휴 시간과 최대 유지 시간을 무한대로 두지 말고, DB 설정에 맞춰 값을 정하자.
{: .prompt-warning }

## 서버 캐시

서버를 늘리면 처리량은 늘지만 요청 하나의 실행 시간이 줄지는 않는다. DB를 확장하지 않고 응답 시간과 처리량을 함께 개선하는 방법이 **캐시**다. DB 조회 결과뿐 아니라 복잡한 계산 결과나 외부 API 응답도 캐시에 담을 수 있다. 캐시 키는 `posts:1`, `posts:hot` 처럼 의미가 드러나게 설계한다.

### 적중률과 삭제 규칙

```text
적중률 = 캐시에서 찾은 건수 / 캐시 조회를 시도한 건수
```

적중률이 높을수록 DB 연동이 줄어 응답 시간, 처리량, DB 부하가 모두 좋아진다. 하지만 캐시는 메모리를 쓰니 용량에 한계가 있고, 가득 차면 무언가를 지워야 한다.

- **LRU**: 가장 오래 사용되지 않은 데이터 삭제
- **LFU**: 가장 적게 사용된 데이터 삭제
- **FIFO**: 먼저 들어온 데이터 삭제

유효 시간(TTL)을 함께 설정해 용량을 관리한다.

### 로컬 캐시 vs 리모트 캐시

| | 로컬 캐시 (Caffeine 등) | 리모트 캐시 (Redis 등) |
| --- | --- | --- |
| 저장 위치 | 서버 프로세스와 같은 메모리 | 별도 프로세스 |
| 장점 | 빠르고 구조가 단순하다 | 크기를 유연하게 늘릴 수 있고, 재시작해도 데이터가 남는다 |
| 단점 | 크기 제한, 재시작하면 데이터가 사라져 적중률이 순간 하락 | 네트워크 통신이 필요해 느리고 구조가 복잡하다 |
| 어울리는 곳 | 데이터가 작고 변경이 드문 경우 (예: 공지 목록) | 데이터가 크거나 배포가 잦은 서비스 |

### 캐시 사전 적재

매달 정해진 날 300만 사용자에게 요금 알림을 보내는 앱을 생각해 보자. 알림을 받은 사용자가 몰려들 때 캐시가 비어 있으면 적중률은 0%이고 부하가 그대로 DB로 간다. 이렇게 트래픽이 몰리는 시점이 예측된다면 **미리 캐시에 넣어 두자.** 적중률이 99%에 가까워지면 응답 시간도 안정되고 DB도 지킬 수 있다.

### 캐시 무효화

원본 데이터가 바뀌면 캐시도 바꾸거나 지워야 한다. 시점은 데이터 성격에 따라 다르다.

1. 민감한 데이터는 **변경 즉시** 무효화한다. (예: 게시글 수정)
2. 변경에 민감한 데이터는 로컬이 아니라 **리모트 캐시**에 둔다. (예: 가격. 서버마다 값이 다르면 곤란하다)
3. 민감하지 않고 작은 데이터는 **TTL로 주기적으로** 갱신한다. (예: 인기 글 목록)

## 가비지 컬렉터와 메모리

Java, Go, Python은 GC가 쓰지 않는 메모리를 알아서 회수해 준다. 편하지만, Java에서는 GC가 도는 동안 애플리케이션이 멈출 수 있어 응답 시간에 영향을 준다. 객체가 많을수록 GC 시간도 길어진다.

- **힙 크기**는 실제 메모리 사용 패턴에 맞춰 조정한다. 너무 작으면 메모리 부족 에러가 난다.
- **한 번에 많은 객체를 만들지 않는다.** 조회 개수를 트래픽 규모와 메모리 크기에 맞춰 제한한다.
- **파일은 스트림으로** 보낸다. 파일 전체를 메모리에 올리는 대신 8KB 단위로 읽어 쓰면, 동시 요청이 100개여도 버퍼는 800KB 수준이다.

## 응답 데이터 압축

응답 시간에는 전송 시간도 포함되고, 전송 시간은 네트워크 속도와 데이터 크기에 달려 있다. 네트워크 속도는 통제할 수 없지만 크기는 줄일 수 있다. HTML, CSS, JS, JSON 같은 텍스트 응답은 압축 효과가 크고, 트래픽 비용도 줄어든다. Nginx 같은 웹 서버는 설정만 추가하면 된다.

> 클라이언트는 `Accept-Encoding: gzip, deflate` 로 지원하는 압축 방식을 알리고, 서버는 그중 하나로 압축한 뒤 `Content-Encoding` 헤더로 사용한 방식을 알려 준다.
{: .prompt-info }

다만 JPEG, ZIP처럼 이미 압축된 데이터는 효과가 없다. 또 방화벽이 압축을 풀어 버리는 경우도 있으니, 압축이 안 된다면 방화벽 설정을 확인하자.

## 정적 자원: 브라우저 캐시와 CDN

이미지, JS, CSS 같은 정적 자원은 같은 URL이면 늘 같은 데이터다. 매번 내려받게 할 이유가 없다.

- **브라우저 캐시**: `Cache-Control: max-age=60` 이나 `Expires` 헤더로 클라이언트가 일정 시간 데이터를 보관하게 한다.
- **CDN**: 브라우저 캐시는 브라우저 단위라서, 동시에 많은 사용자가 처음 접속하면 여전히 트래픽이 몰린다. CDN은 오리진 서버에서 한 번 가져온 콘텐츠를 캐시해 두고 이후 요청에 대신 응답한다. 여러 지역에 서버를 두어 사용자는 가까운 곳에서 받는다.

```text
사용자 → CDN ── (캐시에 없을 때만) ──→ 오리진 서버
          └─ 캐시에 있으면 바로 응답
```

서비스가 성장하기 시작했다면 오리진 트래픽 감소, 빠른 전송, 비용 절감을 위해 CDN 도입을 고려하자.

## 대기 처리

콘서트 예매처럼 짧은 순간 트래픽이 폭증했다가 금방 줄어드는 경우가 있다.

1. **미리 증설한다.** 서버는 클라우드에서 쉽게 늘릴 수 있지만, DB는 쉽게 늘렸다 줄이기 어려워 비용 부담이 크다.
2. **수용할 만큼만 받고 나머지는 대기시킨다.** 증설 없이 안정적으로 서비스할 수 있고, 새로고침하면 순번이 뒤로 밀리니 새로고침으로 인한 트래픽 폭증도 막는다.

## 정리

- 성능 개선은 **측정**에서 시작한다. TPS와 응답 시간을 알고, 느린 지점을 찾는다.
- 확장은 병목에 맞게. 서버를 늘려도 DB나 외부 API가 병목이면 소용없다.
- 커넥션 풀, 캐시, 압축, CDN, 대기 처리는 모두 **같은 자원으로 더 많은 요청을 감당하는 방법**이다.

직접 서비스를 운영하면서 Hikari 커넥션 풀이 꽉 찬 상태에서 요청당 점유 시간을 줄여 처리량을 올려 본 적이 있는데, 이 장을 읽으니 그때 본 지표들이 왜 그렇게 움직였는지 다시 정리됐다.
