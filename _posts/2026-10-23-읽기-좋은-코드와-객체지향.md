> 신촌연합 IT동아리 백엔드 파트 세션에서 발표한 내용을 글로 옮겼습니다. 예시 코드는 이전 기수에서 제가 개발했던 **모앤디**(시술 모델–디자이너 매칭 서비스)를 바탕으로, 설명을 위해 일부러 더 절차지향적으로 바꾼 것입니다.
{: .prompt-info }

## 읽기 좋은 코드란 뭘까?

술술 읽히는 코드? 반은 맞고 반은 아니에요. 제가 생각하는 읽기 좋은 코드는 이런 코드입니다.

- **변경하기 쉽고**
- **의존성이 명확하며**
- **도메인 규칙이 한 곳에 모여 있는** 코드

혹시 이런 상황, 겪어 본 적 있나요?

> "공고 생성할 때 이미지 업로드 정책 바꿔야 하는데... 어디서 처리하고 있었더라?"
> "아;; `createRecruitment` 100줄짜리 메서드 안에 있었네..."

저는 모앤디를 개발하면서 실제로 겪었어요. 이미지 정책 하나 바꾸려고 주석을 따라가며 겨우 위치를 찾았죠. 그 메서드가 대략 이런 모습이었습니다.

```java
@Transactional
public RecruitmentResponseDto createRecruitment(User user, RecruitmentRequestDto dto) {

    // 1. 권한 체크
    if (user.getRole() != Role.DESIGNER) {
        throw new RuntimeException("디자이너만 공고를 생성할 수 있습니다.");
    }

    // 2. Designer 조회
    Designer designer = designerRepository.findByUserId(user.getId())
            .orElseThrow(() -> new RuntimeException("Designer not found"));

    // 3. 이미지 validation
    if (designer.getCategory() == Category.HAIR
            || designer.getCategory() == Category.NAIL) {
        if (dto.imageUrls() == null || dto.imageUrls().isEmpty()) {
            throw new RuntimeException("이미지가 필요합니다.");
        }
    }

    // 4. deadline 계산
    LocalDate deadline = dto.recruitmentSchedule().stream()
            .map(RecruitmentScheduleRequest::recruitmentDate)
            .max(LocalDate::compareTo)
            .orElseThrow(() -> new RuntimeException("schedule is required"));

    // 5. Recruitment 생성
    Recruitment recruitment = Recruitment.builder()
            .designer(designer)
            .title(dto.title())
            // ... 필드 10여 개
            .deadline(deadline)
            .recruitmentStatus(RecruitmentStatus.OPEN)
            .build();

    // 6. 저장
    recruitmentRepository.save(recruitment);

    // 7. SubCategory 처리, 8. Schedule 생성, 9. 이미지 처리 ...
    // (각각 for문을 돌며 연관 엔티티를 만들고 저장)

    // 10. Response DTO 변환
    return new RecruitmentResponseDto(/* ... */);
}
```

권한 체크, 조회, 검증, 생성, 연관 엔티티 저장, DTO 변환까지 **모든 로직이 한 메서드에 몰려 있는 절차지향 코드**예요. 작성한 사람도 나중에 고치기 힘들고, 리뷰하는 사람은 이 메서드가 어디까지 책임지는지 한 줄씩 읽어 봐야 알 수 있어요.

반면 같은 기능을 이렇게 쓸 수도 있습니다.

```java
@Transactional
public RecruitmentResponseDto createRecruitment(User user, RecruitmentRequestDto dto) {
    validateDesignerRole(user);                          // 권한 체크

    Designer designer = designerRepository.findByUserId(user.getId())
            .orElseThrow(() -> new EntityNotFoundException("Designer not found"));

    Recruitment recruitment = Recruitment.create(designer, dto); // 생성은 도메인에 위임

    recruitmentRepository.save(recruitment);
    return RecruitmentResponseDto.from(recruitment);
}
```

메서드는 **흐름만** 제어하고, 각 책임은 메서드와 도메인 객체로 나뉘어 있어요. 이미지 정책을 바꿔야 한다면 어디를 열어야 할지 바로 보이죠. 이렇게 쓰려면 무엇을 알아야 하는지, 지금부터 하나씩 볼게요.

## 객체지향이란

**필요한 데이터를 추상화해 상태와 행위를 가진 객체로 만들고, 객체들 간의 상호작용으로 로직을 구성하는 방식**입니다. 너무 유명하지만, 네 가지 특징부터 짚고 갈게요.

### 추상화

공통적인 속성과 기능을 뽑아 하나의 개념으로 정의하는 거예요. 삼성폰과 아이폰은 달라도 둘 다 "휴대폰"이죠. 공통 기능은 위로 올리고, 새 기종을 만들 때는 고유한 기능만 새로 만들면 됩니다.

![추상화](oop-1-abstraction.png)

코드로 보면, 각자 따로 놀던 자동차 클래스들을

```java
public class SuperCar { public void move() { System.out.println("슈퍼하게 달립니다."); } }
public class SnowCar  { public void move() { System.out.println("겨울에 잘 달립니다."); } }
public class FastCar  { public void move() { System.out.println("빠르게 달립니다."); } }
```

`Car`라는 공통 개념으로 묶으면, 쓰는 쪽은 어떤 차인지 몰라도 한 번에 다룰 수 있어요.

```java
public abstract class Car {
    public abstract void move();
}

List<Car> cars = List.of(new SuperCar(), new SnowCar(), new FastCar());
for (Car car : cars) {
    car.move();
}
```

### 상속

기존 클래스의 특성을 자식 클래스가 물려받아 재사용하는 거예요. 우리가 가장 흔하게 쓰는 예가 `BaseEntity`죠.

```java
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public class BaseEntity {

    @CreatedDate
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    private LocalDateTime deletedAt;

    public void markAsDeleted() { this.deletedAt = LocalDateTime.now(); }
}

@Entity
public class User extends BaseEntity {
    // createdAt, updatedAt을 매번 선언할 필요가 없다
}
```

### 다형성

하나의 인터페이스가 상황에 따라 다르게 동작하는 능력이에요. 저도 한 동아리에선 운영진, 다른 동아리에선 챌린저, 집에서는 막내잖아요?

![다형성 비유](polymorphism-me.png){: width="420" }

객체도 마찬가지예요. 모앤디에서는 디자이너 카테고리마다 공고 이미지 규칙이 달랐어요.

```java
designer.validateRecruitmentImage(dto);
// HAIR면 헤어 규칙, NAIL이면 네일 규칙이 알아서 실행된다

public class HairDesigner extends Designer {
    @Override
    public void validateRecruitmentImage(RecruitmentRequestDto dto) {
        if (dto.imageUrls().size() < 3) {   // 헤어는 포트폴리오 이미지 3장 이상
            throw new IllegalArgumentException("헤어 카테고리는 이미지 3장 이상 필요합니다.");
        }
    }
}

public class NailDesigner extends Designer {
    @Override
    public void validateRecruitmentImage(RecruitmentRequestDto dto) {
        if (dto.imageUrls() == null || dto.imageUrls().isEmpty()) { // 네일은 1장 이상
            throw new IllegalArgumentException("이미지가 필요합니다.");
        }
    }
}
```

Service는 어떤 디자이너인지 몰라도 되고, 나중에 TATTOO 카테고리가 생겨도 **Service는 그대로 두고 클래스만 하나 추가**하면 돼요.

### 캡슐화

데이터와 메서드를 하나로 묶고, 외부에서 알 필요 없는 부분은 감추는 거예요. 자판기에서 콜라를 뽑을 때 내부에서 어떻게 캔이 나오는지 몰라도 되죠. 오히려 내부가 다 공개되면 누군가 드라이버를 들고 와서 뜯어 갈 수도 있고요.

![캡슐화](oop-2-encapsulation.png)

코드에서는 Setter를 떠올리면 쉬워요.

```java
// ❌ 상태가 어디서 바뀌는지 추적할 수 없다
recruitment.setRecruitmentStatus(RecruitmentStatus.CLOSED);

// ✅ 바꾸는 규칙까지 객체 안에
public class Recruitment {
    public void close() {
        if (this.status != RecruitmentStatus.OPEN) {
            throw new IllegalStateException("이미 마감된 공고입니다.");
        }
        this.status = RecruitmentStatus.CLOSED;
    }
}
```

> **Entity에 Setter를 쓰지 말자**
> - 객체 밖 어디서든 상태가 바뀔 수 있어 책임이 흩어지고 디버깅이 어려워진다.
> - 주민번호처럼 바뀌면 안 되는 필드에도 Setter가 생긴다.
> - `close()`, `approve()` 같은 의미 있는 메서드 이름이 코드를 문서처럼 읽히게 한다.

## 코드를 짤 때의 세 가지 기준

### KISS: Keep It Simple, Stupid

코드는 단순하고 이해하기 쉽게. 코드는 컴퓨터가 아니라 사람이 읽으니까, **메서드 이름만 봐도 무슨 일을 하는지** 알 수 있게 쪼개 주세요.

```java
// ❌ 조건 분기를 읽어야 의도가 보인다
if (user.getRole() != Role.DESIGNER) { throw ... }
if (designer.getCategory() == Category.HAIR || designer.getCategory() == Category.NAIL) {
    if (dto.imageUrls() == null || dto.imageUrls().isEmpty()) { throw ... }
}

// ✅ 이름이 곧 설명
validateDesignerRole(user);
designer.validateImageRequirement(dto);
```

### YAGNI: You Aren't Gonna Need It

"나중에 쓸 수도 있으니까~" 하고 만든 코드, 실제로 쓰인 적 있나요?

```java
// ❌ 요구사항에 없는 필드를 미리
public class Recruitment {
    private String title;
    private String content;
    private String videoUrl;      // 나중에 영상 첨부할 수도 있잖아
    private String externalLink;  // 외부 링크 연동할 수도 있잖아
    private Integer viewCount;    // 조회수 생기면 쓸 듯?
}
```

YAGNI가 미래를 무시하라는 뜻은 아니에요. **확장 가능한 구조는 만들어 두되, 구현은 실제로 필요할 때** 하라는 거예요. 생길 수도 있는 기능은 팀 문서나 주석에 메모해 두면 충분합니다. 저는 주로 팀 노션에 적어 두는 편이에요.

### DRY: Don't Repeat Yourself

같은 코드가 여러 곳에 흩어져 있으면, 바꿀 때 전부 찾아서 고쳐야 해요. 공고 생성과 수정에 똑같은 이미지 검증이 들어가 있다면 한 곳으로 모읍시다.

```java
public class RecruitmentImageValidator {
    public void validateImageRequirement(RecruitmentRequestDto dto) {
        if (requiresImage() && hasNoImage(dto)) {
            throw new IllegalArgumentException("이미지가 필요합니다.");
        }
    }
}
```

## SOLID, 그중 두 가지

| 원칙 | 한 줄 요약 |
| --- | --- |
| **SRP** | 클래스는 단 하나의 책임만 가져야 한다 |
| OCP | 확장에는 열려 있고, 수정에는 닫혀 있어야 한다 |
| LSP | 자식 타입은 언제나 부모 타입으로 바꿔 쓸 수 있어야 한다 |
| ISP | 인터페이스는 쓰임에 맞게 잘게 나눠야 한다 |
| **DIP** | 구현이 아니라 인터페이스에 의존해야 한다 |

너무 유명한 개념이라 전부 다루기보다, 오늘 예시와 직접 연결되는 두 가지만 볼게요.

### SRP: 하나의 클래스는 하나의 이유로만 바뀌어야 한다

처음의 `createRecruitment`는 바뀌어야 할 이유가 너무 많아요.

- 권한 정책이 바뀌면 → `createRecruitment` 수정
- 이미지 검증 조건이 바뀌면 → `createRecruitment` 수정
- 마감일 계산이 바뀌면 → `createRecruitment` 수정
- 스케줄 저장 방식이 바뀌면 → 또 `createRecruitment` 수정

그 결과 이미지 로직을 고쳤는데 마감일 계산이 깨지고, 리뷰어와 새 팀원은 이 메서드가 뭘 하는지 파악하느라 시간을 씁니다. 책임을 나누면, 수정할 일이 생겼을 때 **해당 메서드만 열면** 돼요.

### DIP: 구현 클래스가 아니라 인터페이스에 의존하라

```java
// ❌ JPA 구현체에 강하게 묶임
public class RecruitmentService {
    private final JpaDesignerRepository designerRepository;
}

// ✅ 인터페이스에만 의존
public class RecruitmentService {
    private final DesignerRepository designerRepository;
}
```

이렇게 하면 저장소를 `MongoDesignerRepository`로 바꿔도 Service 코드는 한 줄도 바뀌지 않아요. 테스트할 때 가짜(Fake) 구현체를 끼워 넣기도 쉬워지고요.
