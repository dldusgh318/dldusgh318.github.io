## 무엇을 봐야 할까?

도구도 중요하지만, 그보다 더 중요한 건 **"어떤 지표를 봐야 하는가"**예요.

### 서버 · 인프라: 리소스가 정상 범위에 있는가?

**CPU 사용률.** Spring Boot 서버의 CPU는 요청 처리, 비즈니스 로직 실행, GC, 멀티스레딩, I/O 조정까지 하는 일이 많아 부하가 쉽게 생겨요. 순간 피크는 흔하니 **"90% 이상이 1분 넘게 지속"**처럼 시간 조건을 함께 걸어야 진짜 과부하를 잡을 수 있어요.

**메모리 (JVM Heap).** 메모리 누수와 OOM을 미리 잡는 게 목표예요. 이런 흐름이 보이면 위험 신호입니다.

```text
Heap 사용률이 점점 상승
  ↓
GC가 점점 자주 발생
  ↓
Full GC 동안 수백 ms ~ 수 초간 애플리케이션 정지
  ↓
응답시간 급증
```

**디스크 사용률.** 디스크가 100%가 되면 파일 업로드, 로그 저장, DB 쓰기, 소켓 생성까지 전부 실패해요. 로그 저장이 안 되니 **원인 파악조차 못 하게** 되고요. 로그 파일은 생각보다 훨씬 빨리 쌓이니 롤링 설정은 필수입니다. (저도 실제로 로그가 쌓여 디스크가 가득 찬 장애를 겪었어요.)

**네트워크 트래픽.** 수신이 급증하면 DDoS나 비정상 업로드를, 송신이 급증하면 데이터 유출이나 비정상 다운로드를 의심해 볼 수 있어요.

**DB 커넥션 풀 (HikariCP).** 커넥션이 바닥나면 이렇게 번집니다.

```text
커넥션 풀 90% 이상 사용
  ↓
새 요청이 커넥션을 기다림 (Pending)
  ↓
스레드가 커넥션을 기다리며 붙잡혀 있음
  ↓
서비스 전체 응답시간 급증
```

**스레드 풀.** Tomcat의 기본 최대 스레드는 200개예요. 활성 스레드가 200개에 가까워지면 새 요청이 큐에서 기다리고, 응답시간이 늘고, 타임아웃과 에러가 이어져요. 그리고 **스레드 풀과 커넥션 풀은 연결돼 있어요.** 커넥션이 고갈되면 스레드가 커넥션을 기다리느라 반환되지 못하고, 결국 스레드 풀도 같이 고갈되니 둘은 꼭 같이 봐야 해요.

### 서비스: 사용자가 체감하는 품질은?

**응답시간 (Latency).** 평균보다 **p99**(상위 1% 느린 요청)를 보는 게 체감 품질과 병목 탐지에 좋아요.

```text
# 최근 5분간 상위 1% 응답시간(ms)
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket[5m]))) * 1000
```

**TPS.** 초당 처리하는 요청 수예요. API별로 나눠 보면 트래픽이 어디로 몰리는지 알 수 있어요.

```text
sum(rate(http_server_requests_seconds_count[1m]))                 # 전체 TPS
sum by (uri)(rate(http_server_requests_seconds_count[1m]))        # API별 TPS
```

**에러율.** 전체 요청 대비 5xx 비율이에요.

```text
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/ sum(rate(http_server_requests_seconds_count[5m])) * 100
```

기준값은 트래픽이 많은 시간대의 TPS와 응답시간을 측정해 보고, 그걸 바탕으로 정하는 게 좋아요.

### 한눈에 보는 기준표

| 레벨 | 지표 | 목적 | 정상 | 위험 신호 |
| --- | --- | --- | --- | --- |
| 인프라·서버 | CPU | 과부하 감지 | < 70% | > 90% (1분 이상) |
| | JVM Heap | 메모리 누수 감지 | < 80% | > 85% |
| | Full GC | 응답 지연 원인 | < 1회/분 | > 1회/분 |
| | 디스크 | 시스템 마비 방지 | < 80% | > 85% |
| | 네트워크 | 비정상 트래픽 감지 | 평상시 수준 | 평상시의 2배 이상 |
| | DB 커넥션 풀 | 요청 대기 방지 | < 80% | > 90% |
| | 스레드 풀 | 요청 처리 여력 | < 70% | > 80% (5분 이상) |
| | Redis Hit Ratio | 캐시 효율 | > 90% | < 70% |
| 서비스 | p99 응답시간 | 체감 품질 | < 500ms | > 1000ms |
| | 5xx 에러율 | 신뢰도 | < 0.1% | > 1% (5분 이상) |
| | TPS | 처리량 | 평상시 수준 | 급증·급감 |

## 알림으로 받아 보기

대시보드를 수시로 들여다보지 않는 이상 이상을 바로 알기는 어려워요. 그래서 **Grafana Alert Rules + Slack/Discord Webhook**으로 알림을 받습니다. ([연동 방법 참고](https://pixx.tistory.com/339))

제가 정한 알림 기준은 이래요.

- CPU 80% 이상 5분 지속 시 경고, 95% 이상이면 즉시
- 메모리 80% 이상 지속 시 경고, 95% 이상이면 즉시
- 디스크 95% 이상
- HikariCP 활성 커넥션이 최대의 90% 이상
- Tomcat 활성 스레드가 최대의 90% 이상
- 애플리케이션이 갑자기 종료됐을 때
- **WARN** 로그가 1분에 20개 이상
- **ERROR** 로그가 1개라도 발생 (너무 잦아지면 1분에 5개 이상으로 조정)

## 실전! 모니터링 환경 만들기

**Alloy + Loki + Grafana + Prometheus**로 구성합니다.

### 0. 의존성

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
    implementation 'io.micrometer:micrometer-registry-prometheus'
}
```

### 1. 로그를 파일로 남기기 (Logback)

Alloy가 읽을 수 있도록 로그를 파일로 남기고, 롤링 정책으로 디스크가 가득 차지 않게 막아요.

<details markdown="1">
<summary><code>src/main/resources/logback-spring.xml</code></summary>

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>logs/application.log</file>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>logs/application-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <maxFileSize>10MB</maxFileSize>      <!-- 파일 하나당 최대 10MB -->
            <maxHistory>30</maxHistory>          <!-- 최대 30일 보관 -->
            <totalSizeCap>1GB</totalSizeCap>     <!-- 전체 최대 1GB -->
        </rollingPolicy>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE" />
        <appender-ref ref="FILE" />
    </root>
</configuration>
```

</details>

### 3. Loki · Alloy · Prometheus 설정

**Loki**는 로그를 7일만 보관하고, 지난 로그는 자동으로 지우도록 설정했어요.

<details markdown="1">
<summary><code>loki-config.yml</code></summary>

```yaml
auth_enabled: false            # 인증 없이 로그 수신

server:
  http_listen_port: 3100
  grpc_listen_port: 9096

common:
  instance_addr: 127.0.0.1
  path_prefix: /loki
  storage:
    filesystem:
      chunks_directory: /loki/chunks
      rules_directory: /loki/rules
  replication_factor: 1
  ring:
    kvstore:
      store: inmemory

schema_config:
  configs:
    - from: 2020-10-24
      store: tsdb               # tsdb 방식으로 인덱싱
      object_store: filesystem
      schema: v13
      index:
        prefix: index_
        period: 24h

limits_config:
  retention_period: 168h       # 로그 보존 7일
chunk_store_config:
  max_look_back_period: 168h

compactor:
  working_directory: /loki/compactor
  shared_store: filesystem
  compaction_interval: 10m     # 10분마다 압축
  retention_enabled: true      # 보존 기간 지난 로그 자동 삭제
  retention_delete_delay: 2h
```

</details>

**Alloy**는 로그 파일을 읽고, 시간과 로그 레벨을 뽑아 레이블을 붙인 뒤 Loki로 보내요. 기존 Promtail 설정이 있다면 명령 한 줄로 변환할 수 있어요.

```bash
alloy convert --source-format=promtail --output=alloy-config.yml promtail-config.yml
```

<details markdown="1">
<summary><code>alloy-config.yml</code></summary>

```hcl
// 1. 로그 파일 수집
loki.source.file "spring_boot" {
  targets = [{
    __address__ = "localhost",
    __path__    = "/var/log/spring-boot/*.log",
    app         = "log-demo",       // 어떤 서비스인지
    job         = "spring-boot",    // 어떤 방식으로 수집했는지
  }]
  forward_to = [loki.process.spring_boot.receiver]
  legacy_positions_file = "/tmp/positions.yaml"   // 어디까지 읽었는지 기록
}

// 2. 파싱: 시간과 로그 레벨 추출
loki.process "spring_boot" {
  forward_to = [loki.write.default.receiver]

  stage.regex {
    expression = "^(?P<timestamp>\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}\\.\\d{3})"
  }
  stage.regex {
    expression = "\\[.*?\\]\\s+(?P<level>(TRACE|DEBUG|INFO|WARN|ERROR))"
  }
  stage.labels {
    values = { level = null }     // level을 Loki 레이블로 등록
  }
  stage.timestamp {
    source   = "timestamp"
    format   = "2006-01-02 15:04:05.000"
    location = "Asia/Seoul"
  }
}

// 3. Loki로 전송
loki.write "default" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}
```

</details>

> `job`과 `app` 레이블은 이렇게 나눠 쓰면 편해요. `{job="spring-boot"}`로 수집 방식 기준 전체를, `{app="user-service"}`처럼 특정 서비스만 골라 볼 수 있어요.
{: .prompt-tip }

**Prometheus**는 15초마다 앱의 메트릭을 가져와요.

```yaml
# prometheus-config.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: 'server_metric'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets: ['host.docker.internal:8080']
        labels:
          instance: 'prod_server'
```

### 4. Docker Compose로 띄우기

<details markdown="1">
<summary><code>docker-compose.yml</code></summary>

```yaml
services:
  loki:                                   # 로그 저장소
    image: grafana/loki:2.9.0
    ports: ["3100:3100"]
    environment: [TZ=Asia/Seoul]
    volumes:
      - ./loki-config.yml:/etc/loki/local-config.yaml

    networks: [loki-network]

  alloy:                                  # 로그 수집 (Promtail 대체)
    image: grafana/alloy:latest
    ports: ["12345:12345"]
    environment: [TZ=Asia/Seoul]
    volumes:
      - ./alloy-config.yml:/etc/alloy/config.alloy
      - ./logs:/var/log/spring-boot       # Spring 로그 파일 경로
      - ./alloy-data:/tmp
    command: run --server.http.listen-addr=0.0.0.0:12345 --storage.path=/var/lib/alloy/data /etc/alloy/config.alloy
    depends_on: [loki]
    networks: [loki-network]

  grafana:                                # 시각화
    image: grafana/grafana:10.1.0
    ports: ["3000:3000"]
    environment:
      - GF_SECURITY_ADMIN_USER=admin
      - GF_SECURITY_ADMIN_PASSWORD=admin  # 실제로는 꼭 바꾸세요
      - GF_USERS_ALLOW_SIGN_UP=false
      - TZ=Asia/Seoul
    volumes:
      - grafana-data:/var/lib/grafana
    depends_on: [loki]
    networks: [loki-network]

  prometheus:                             # 메트릭 수집·저장

    ports: ["9090:9090"]

      - ./prometheus-config.yml:/etc/prometheus/prometheus.yml

networks:
  loki-network:                           # 서비스 이름만으로 서로 통신
    driver: bridge

volumes:
  loki-data:
  grafana-data:
```

### 7. 시나리오로 확인하기

- **에러 발생 모니터링**: 에러를 일으키는 API를 호출하면 에러 개수 패널이 올라가고, 로그 스트림에 에러 메시지가 찍히고, 시간대별 로그량이 튀는 걸 볼 수 있어요.
- **특정 사용자 추적**: `{job="spring-boot"} |= "testuser"`로 검색하면 그 사용자의 요청 흐름만 모아 볼 수 있어요.

## 마무리: 메트릭 → 로그 → 트레이스로 좁혀 가기

마지막으로, 세 가지 신호를 어떻게 같이 쓰는지 예시 하나로 정리할게요.

```text
상황: 공고 생성 API 응답시간이 500ms → 5000ms로 급증

1단계 (메트릭)
  p99 = 5000ms                       ← 이상 감지
  CPU, 메모리는 정상
  DB 커넥션 풀 사용률 95%            ← 이상!

2단계 (로그)
  [WARN] HikariPool - Connection is not available, request timed out

3단계 (트레이스)
  S3 업로드 구간에서 4200ms 소비
  → @Transactional 안에서 S3를 호출하고 있었다
  → 트랜잭션이 커넥션을 붙잡은 채 S3 응답을 기다림

원인: 트랜잭션 범위 안에 외부 API 호출
해결: S3 업로드를 트랜잭션 밖으로 분리
```

메트릭이 "**무엇이**" 이상한지, 로그가 "**왜**"를, 트레이스가 "**어디서**"를 알려 줬어요. 도구를 설치하는 것보다, 이렇게 **좁혀 가는 순서**를 몸에 익히는 게 모니터링의 핵심이라고 생각합니다.
