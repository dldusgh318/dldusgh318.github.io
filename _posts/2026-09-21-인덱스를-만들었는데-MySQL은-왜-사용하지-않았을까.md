최근에 청바지 프로젝트를 다시 뜯어보면서, 내가 만든 API가 실제로 어디에서 시간을 쓰고 있는지 제대로 확인해보고 싶었다.

사실 처음부터 “이 API에 심각한 성능 문제가 있다!”에서 시작한 건 아니었다. MVP 배포를 끝내고 나서 그동안 구현해온 것들을 다시 보다 보니, 문득 이런 생각이 들었다.

**API가 느려지면 나는 어디서부터 원인을 찾을 수 있을까?**

예전 같았으면 일단 쿼리를 열어보거나, 인덱스를 추가하거나, Connection Pool이 부족한 건 아닌지부터 생각했을 것 같다. 그런데 이번에는 추측으로 뭔가를 바꾸기 전에, 실제 지표를 보면서 어디에서 시간이 사용되고 있는지부터 따라가 보기로 했다.

대상은 청바지의 **최근 조회 정책 API**였다.

사용자가 최근에 확인한 정책을 최신순으로 보여주는 API인데, 단순히 최근 조회 기록만 가져오는 건 아니다. 현재 노출 가능한 정책인지, 지역 조건에 맞는지 등을 확인한 뒤 최종적으로 필요한 정책만 반환한다.

테스트를 위해 최근 조회 이벤트 10만 건을 만들었고, HikariCP Pool Size는 10으로 고정했다. 15초 동안 워밍업한 뒤 20 VU로 60초 동안 부하를 주었다.

여기서 나오는 숫자는 실제 운영 트래픽을 측정한 값은 아니다. 동일한 데이터와 부하 조건에서 변경 전후를 비교하기 위해 따로 구성한 로컬 벤치마크 환경이다.

## **Pool을 늘리면 되는 거 아닌가?**

가장 먼저 Grafana에서 Application 지표를 확인했다.

![](01.png)

HTTP p95는 약 **535ms**, 처리량은 약 **52 req/s**였다.

그런데 같이 수집하고 있던 HikariCP 지표를 보니 조금 더 눈에 들어오는 게 있었다.

Connection Pool은 10개가 전부 사용되고 있었고, pending 역시 p95 기준 10까지 올라가 있었다.

처음 든 생각은 정말 단순했다.

**“Connection이 부족하면 Pool을 늘리면 되는 거 아닌가?”**

그런데 조금 생각해보니 이상했다.

Connection 개수를 늘린다고 해서 DB가 갑자기 더 많은 일을 처리할 수 있게 되는 건 아니다. 애플리케이션에서 Connection을 기다리던 요청이 DB 안쪽에서 다른 자원을 기다리게 될 수도 있다.

HikariCP 쪽에서도 Pool을 단순히 크게 만드는 것보다 애플리케이션 레벨에서 먼저 개선할 부분이 없는지 살펴볼 것을 권하고 있다.

그래서 Pool Size를 건드리기 전에 질문을 바꿔봤다.

**“Connection은 왜 이렇게 오래 반환되지 않고 있을까?”**

Grafana만 봐서는 여기까지였다.

Connection을 기다리는 요청이 있다는 건 알 수 있었지만, 어떤 작업이 Connection을 오래 잡고 있는지는 알 수 없었다.

그래서 한 단계 더 내려가 보기로 했다.

## **어떤 SQL이 시간을 쓰고 있을까?**

MySQL Performance Schema에서 최근 조회 API를 실행할 때 어떤 SQL들이 시간을 사용하고 있는지 확인했다.

그중 눈에 들어온 건 크게 두 개였다.

최근 조회 정책을 실제로 가져오는 **List Query는 평균 약 122ms**, 전체 개수를 구하는 **Count Query는 약 42ms**를 사용하고 있었다.

일단 더 큰 시간을 쓰고 있던 List Query부터 보기로 했다.

![](02.png)

그중 눈에 들어온 건 크게 두 개였다. 최근 조회 정책을 실제로 가져오는 List Query는 평균 약 122ms, 전체 개수를 구하는 Count Query는 약 42ms를 사용하고 있었다.

처음에는 최신 조회 이력을 가져오는 데 적절한 인덱스가 없어서 느린 거라고 생각했다.

최근 조회 정책이라면 결국 특정 사용자의 조회 이력을 최신순으로 읽어야 한다. 그래서 `user_id`, `viewed_at DESC`, `policy_id DESC` 순서의 인덱스를 추가했다.

```SQL
CREATE INDEX idx_recent_viewed_policy_user_viewed_policy
    ON recent_viewed_policy (user_id, viewed_at DESC, policy_id DESC);
```

그리고 같은 조건에서 다시 측정했다.

10만 건 기준으로 기존 벤치마크에서는 HTTP p95가 약 **634ms → 535ms**, 처리량도 약 **41 req/s → 47 req/s** 정도로 변했다.

수치만 보면 꽤 그럴듯했다.

여기까지만 보고 끝냈으면 아마 포트폴리오에 "인덱스를 추가하여 조회 성능을 개선했습니다." 라고 적었을 것 같다.


그런데 뭔가 찝찝했다.

**“진짜 내가 만든 인덱스 때문에 빨라진 게 맞나?”**

그래서 `EXPLAIN ANALYZE`를 확인했다.

MySQL의 `EXPLAIN ANALYZE`는 실제 쿼리를 실행하면서 각 iterator의 실제 수행 시간, 반환 row 수, loop 수 등을 같이 보여준다.  
그래서 단순히 “이 인덱스를 쓸 것 같다”가 아니라 실제 실행 과정까지 확인할 수 있다.

결과를 봤는데,

**MySQL은 내가 새로 만든 인덱스를 사용하고 있지 않았다.**

![](03.png)
?

당연히 새 인덱스를 타고 빨라졌을 거라고 생각했는데, 실제 실행 계획에서는 기존 `idx_recent_viewed_policy_user_policy_viewed`를 사용하고 있었다. 새로 만든 `idx_recent_viewed_policy_user_viewed_policy`는 선택되지 않았다. 심지어 1만 건 데이터에서는 인덱스를 추가한 뒤 결과가 더 안 좋게 나오기도 했다.

결국 앞에서 나온 숫자만 가지고 **“새 인덱스 덕분에 빨라졌다”**고 말할 수 없었다.

MySQL은 쿼리마다 여러 Access Path를 검토하고 통계와 비용 등을 바탕으로 실행 계획을 선택한다. 인덱스가 존재한다는 사실 자체가 그 인덱스를 선택한다는 의미는 아니다. MySQL 문서에서도 optimizer가 index 선택 등에 key distribution을 사용한다고 설명한다.

이번에 그걸 꽤 직접적으로 체감했다.

**인덱스를 만들었다고 해서, DB가 그 인덱스를 사용하는 건 아니었다.**

그래서 여기서 질문을 바꿨다.

“어떤 인덱스를 더 만들어야 하지?”가 아니라,  
**“애초에 왜 Policy부터 읽고 있지?”** 로..

## **필요한 건 6개인데, 왜 4,300개를 정렬하고 있지?**

`EXPLAIN ANALYZE`를 조금 더 자세히 봤다.

실행 계획을 따라가 보니 기존 쿼리는 대략 이런 식으로 움직이고 있었다.

> **Policy 10,000건 → Recent History 조회 × 9,000 → 최신 조회 여부 확인 × 8,600 → 후보 약 4,300건 → Sort → LIMIT 6**

결국 필요한 건 6개인데, Policy에서 시작해 수천 번의 조회와 조건 확인을 거친 뒤 약 4,300개의 후보를 만들고 있었다. 그리고 마지막에 이걸 다시 정렬해서 6개만 반환했다.

여기서부터 좀 이상하게 느껴졌다.

**“나는 최근 본 정책 6개가 필요한데, 왜 4천 개가 넘는 후보를 만든 다음 정렬하고 있지?”**

그제야 질문이 또 바뀌었다.

처음에는 "어떤 인덱스를 추가해야 하지?" 였다면,

 이제는 **애초에 어디서부터 읽기 시작해야 하지?** 가 됐다.

최근 조회 정책 API에서 내가 정말 원하는 데이터는 이름 그대로 **사용자의 최근 조회 이력**이다.

그렇다면 모든 Policy에서 시작해서 “이 사용자가 최근에 봤나?”를 확인하는 것보다, 사용자의 조회 이력을 최신순으로 읽으면서 “이 Policy가 현재 보여줄 수 있는 정책인가?”를 확인하는 게 훨씬 자연스러워 보였다.

그래서 조회의 시작점을 **Policy → Recent History**로 바꿨다.

![](04.png)

변경 후 `EXPLAIN ANALYZE`에서는 최신 조회 이력 쪽에서 약 7개의 row를 읽고 조건을 확인한 뒤 필요한 6개를 반환했다. 마지막 Sort도 사라졌다.

격리해서 실행한 `EXPLAIN ANALYZE` 기준으로 List Query는 약 **29.2ms → 0.52ms**까지 줄었다.

부하를 주고 Performance Schema에서 다시 확인했을 때도 기존 List Query 평균 약 **148ms → 0.69ms**로 차이가 났다.

```
Limit: 6 rows
└─ Nested loop inner join
　 ├─ Filter: recent.viewed_at = MAX(…)
　 │　└─ Covering index lookup on recent
　 │　　　using idx_recent_viewed_policy_user_viewed_policy
　 │　　　actual rows=7
　 └─ Single-row index lookup on policy using PRIMARY
```

이번에는 Recent History에서 시작하면서 새로 만든 인덱스가 실제 실행 계획에 사용됐다. 약 7개의 row를 읽고 Policy를 PK로 확인한 뒤 필요한 6개를 반환했고, 기존에 있던 마지막 Sort도 사라졌다.

격리해서 실행한 EXPLAIN ANALYZE 기준으로 List Query는 약 29.2ms → 0.52ms까지 줄었다.

앞의 값은 쿼리를 격리해서 `EXPLAIN ANALYZE`로 실행했을 때의 결과이고, 뒤의 값은 부하 테스트 중 Performance Schema에서 확인한 평균 실행 시간이다.

숫자가 크게 줄었다는 것보다 내가 더 흥미롭게 느낀 건 **인덱스를 추가했을 때가 아니라 데이터를 읽기 시작하는 위치를 바꿨을 때 실행 계획 자체가 달라졌다는 점**이었다.

## **오 빨라졌다. 끝!… 은 아니었다**

Access Path를 바꾸고 나서 다시 요청 전체를 봤다.

그런데 쿼리가 또 보였다.

Native Query 결과를 Entity로 가져온 뒤 연관 데이터를 사용하는 과정에서 Lazy Loading이 발생하면서, 페이지 하나를 조회할 때 추가 SELECT가 5번 실행되고 있었다.

Access Path는 크게 줄였지만, **요청 전체로 보면 아직 줄일 수 있는 DB 작업이 남아있었던 것**이다.

그래서 Batch Fetch를 적용해 개별적으로 발생하던 5번의 SELECT를 하나의 IN Query로 묶었다.

이 변화는 앞선 Access Path 변경만큼 크지는 않았다.

- p95: 190ms → 178ms  
- Throughput: 135 → 149 req/s  
- SELECT/request: 9.91 → 5.97

여기까지 확인하고 나니, 처음 봤던 Grafana 지표로 다시 돌아가 보고 싶었다.

**쿼리 하나가 빨라진 게 아니라, 실제 요청 전체에서도 변화가 있었을까?**


## **다시 Grafana로 돌아와보니**

같은 조건으로 다시 부하를 주었다.

![](05.png)

|  | **Before** | **After** |
| --- | --- | --- |
| HTTP p95 | 535ms | **239ms** |
| Throughput | 52 req/s | **132 req/s** |
| SELECT DB time/request | 165ms | **43ms** |
| Hikari Pool | 10 | **10** |


처음과 비교하면 HTTP p95는 약 **535ms → 239ms**, 처리량은 약 **52 → 132 req/s**로 변했다.

요청 하나당 SELECT가 사용한 DB 시간도 약 **165ms → 43ms**까지 줄었다.

그런데 여기서 또 하나 재미있는 게 있었다.

**HikariCP Pool Size는 처음부터 끝까지 10으로 그대로였다.**

그리고 변경 후에도 active/pending p95는 여전히 10이었다.

즉,Connection Pool 병목을 해결했다고 표현하면 정확하지 않았다..

Pool saturation 자체가 사라진 게 아니기 때문이다

대신 Connection을 사용하는 평균 시간을 같이 보면 acquire time은 약 **91.8ms → 35.5ms**, usage time은 약 **95.1ms → 38.0ms**로 줄었다.

내가 이해한 이번 결과는 이쪽에 더 가까웠다.

**Connection을 늘린 게 아니라, 하나의 요청이 DB에서 해야 하는 일을 줄였다.**

같은 10개의 Connection이더라도 하나의 요청이 더 빨리 반환하면 다음 요청이 사용할 수 있다. 실제로 이번 실험에서는 Pool을 늘리지 않은 상태에서 처리량이 증가했다.

처음 Grafana에서 Connection 10개가 꽉 찬 걸 봤을 때 Pool Size부터 늘렸다면 이 흐름까지 보지 못했을 것 같다.

## **결국 처음 생각했던 문제와 조금 달랐다**

처음에는 Connection Pool이 꽉 찬 걸 봤어서서 Pool이 부족한 건가 생각했다.

그러나 SQL을 확인해보니 List Query가 오래 걸리고 있어 Index가 부족한 건가 생각했다.

그런데 Index를 만들어도 DB는 그 Index를 쓰지도 않았다.

그래서 실행 계획을 다시 보니 필요한 건 6개인데 약 4,300개의 후보를 만들고 정렬하고 있었다.

그제서야 문제를 보는 질문이

**“어떤 Index가 필요한가?” → “DB는 지금 어떤 순서로 데이터를 읽고 있는가?”** 로 바뀌었다..

이번에 성능 숫자가 좋아진 것도 물론 좋았다.

그런데 개인적으로는 `p95 -55%`보다 이 과정이 더 많이 남았다.

예전에는 성능 문제를 만나면 바로 해결 방법부터 떠올렸던 것 같다.

> 인덱스를 붙여볼까?…
캐시를 넣어볼까?…  
Pool을 늘려볼까?….  
> 

이번에는 반대로 지표를 하나씩 따라가면서 질문을 바꿔봤다.

> **왜 Connection을 오래 잡고 있지??
어떤 SQL이 오래 걸리지??  
Index를 만들었는데 왜 안 쓰지??  
필요한 건 6개인데 왜 4,300개를 정렬하지??**  
> 

그리고 마지막 질문까지 가고 나서야 Access Path를 바꾸게 됐다.

아직 끝난 것은 아니다!!!!..

List Query는 많이 줄었지만 Count Query는 부하 환경에서 여전히 평균 **약 41ms**를 사용하고 있다.

여기에 캐시를 붙이는 방법도 생각해볼 수 있지만 이번에 해결해보고 나니 바로 Redis부터 붙이고 싶지는 않다.

그 전에 먼저 확인하고 싶은 게 있다.

**첫 화면에서 정확한 `totalCount`가 정말 필요한가?**

정확한 전체 개수가 꼭 필요하지 않다면 Count Query 자체를 매번 수행해야 하는 이유가 달라진다. 반대로 정확한 값이 정말 필요하다면 그때 캐시의 invalidation이나 key cardinality 비용까지 같이 비교해보고 싶다.

이번 작업을 하면서 남은 건 결국 이런 생각이었다.

**인덱스를 만들기 전에 쿼리를 보고,쿼리를 바꾸기 전에 DB가 실제로 어떻게 읽고 있는지 확인하자.**

다음에 Grafana에서 Connection Pool이 꽉 찬 걸 보더라도, 아마 Pool Size부터 늘리지는 않을 것 같다.
