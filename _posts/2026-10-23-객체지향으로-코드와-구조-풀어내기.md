## 실제로 리팩토링해 보기

1편에서 본 원칙들을 처음의 `createRecruitment`에 하나씩 적용해 볼게요.

### STEP 1. 메서드 분리 (KISS · SRP)

긴 로직마다 이름을 붙여 메서드로 뺍니다. 이것만으로도 흐름이 훨씬 잘 보여요.

```java
@Transactional
public RecruitmentResponseDto createRecruitment(User user, RecruitmentRequestDto dto) {
    validateDesignerRole(user);                       // 디자이너 권한 체크

    Designer designer = findDesigner(user);

    validateImageRequirement(designer, dto);          // 이미지 검증
    LocalDate deadline = calculateDeadline(dto);      // 공고 마감일 계산

    Recruitment recruitment = Recruitment.builder()
            .designer(designer)
            // ...
            .deadline(deadline)
            .build();

    recruitmentRepository.save(recruitment);
    return RecruitmentResponseDto.from(recruitment);
}
```

### STEP 2. 생성 책임을 도메인으로 (SRP · DRY)

검증과 마감일 계산은 사실 `Recruitment`라는 개념에 속한 규칙이에요. 생성 책임을 도메인 객체로 옮깁니다.

```java
public class Recruitment {

    public static Recruitment create(Designer designer, RecruitmentRequestDto dto) {
        validateImageRequirement(designer, dto);
        LocalDate deadline = calculateDeadline(dto);

        return Recruitment.builder()
                .designer(designer)
                // ...
                .deadline(deadline)
                .recruitmentStatus(RecruitmentStatus.OPEN)
                .build();
    }

    private static void validateImageRequirement(Designer designer, RecruitmentRequestDto dto) { /* ... */ }
    private static LocalDate calculateDeadline(RecruitmentRequestDto dto) { /* ... */ }
}
```

### STEP 3. 엔티티 책임 강화

연관 엔티티(서브카테고리, 스케줄, 이미지)를 만드는 일도 `Recruitment`에게 맡깁니다.

```java
@Entity
public class Recruitment {

    @OneToMany(mappedBy = "recruitment", cascade = CascadeType.ALL, orphanRemoval = true)
    private final List<RecruitmentSchedule> schedules = new ArrayList<>();

    @OneToMany(mappedBy = "recruitment", cascade = CascadeType.ALL, orphanRemoval = true)
    private final List<RecruitmentImage> images = new ArrayList<>();

    public static Recruitment create(Designer designer, RecruitmentRequestDto dto) {
        // ... 검증, 마감일 계산, builder
        recruitment.addSubCategories(dto.subCategoryList());
        recruitment.addSchedules(dto.recruitmentSchedule());
        recruitment.addImages(dto.imageUrls());
        return recruitment;
    }

    private void addImages(List<String> imageUrls) {
        if (imageUrls == null) return;
        for (String url : imageUrls) {
            this.images.add(new RecruitmentImage(this, url));
        }
    }
    // addSubCategories, addSchedules도 같은 방식
}
```

"연관 엔티티 생성까지 엔티티가 해도 되나?" 싶을 수 있어요. 저도 궁금해서 교수님께 여쭤봤는데, 핵심은 **응집도**였어요. 공고를 만드는 규칙이 데이터를 가진 객체 안에 모이니 응집도가 올라가는 거죠.

### 완성본

```java
@Transactional
public RecruitmentResponseDto createRecruitment(User user, RecruitmentRequestDto dto) {
    validateDesignerRole(user);                                   // 권한 체크
    Designer designer = findDesigner(user);                       // 조회
    Recruitment recruitment = Recruitment.create(designer, dto);  // 생성은 도메인에 위임
    recruitmentRepository.save(recruitment);                      // 저장
    return RecruitmentResponseDto.from(recruitment);              // 반환
}
```

100줄이 다섯 줄이 됐어요. 이제 이미지 정책이 바뀌면 `Recruitment`만 열면 됩니다.

### Rich Domain vs Anemic Domain

이렇게 하다 보면 도메인 객체가 점점 커져요. 여기서 두 가지 스타일이 갈립니다.

|  | Anemic Domain | Rich Domain |
| --- | --- | --- |
| Entity 역할 | 데이터 보관 | 데이터 + 비즈니스 로직 |
| Service 역할 | 모든 로직 처리 | 흐름만 책임 |
| 문제점 | Service 비대화, 중복 코드 | 초기 설계 비용 |
| 관점 | 절차지향에 가까움 | 객체지향 |

정답은 없으니 각자 서비스에 맞는 쪽을 고민해 보시면 돼요. 저는 리치 도메인을 좋아합니다.

## Service에서 Service를 부를까, Repository를 부를까

프로젝트를 하다 보면 기능을 재사용하려고 Service가 다른 Service를 주입받고, 그러다 결국 이런 에러를 만나곤 해요.

```text
***************************
APPLICATION FAILED TO START
***************************

The dependencies of some of the beans in the application context form a cycle:

┌─────┐
|  postService
↑     ↓
|  memberService
↑     ↓
|  boardService
└─────┘
```

저도 Service 단위로 기능을 재사용하다가 순환 참조를 여러 번 겪었어요. 원인은 **아키텍처적으로 정해 둔 기준 없이** 코딩했기 때문이었죠. 그럼 기준을 어떻게 세울까요? `PostService`가 게시글, 회원, 게시판 정보를 모두 필요로 하는 상황을 가정해 볼게요.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| **1. 다른 도메인의 Repository를 직접 주입** | 작은 프로젝트에서 편하고, 순환 참조가 없음 | Repository가 늘수록 복잡해지고, 테스트 때 전부 Mock해야 함 |
| **2. 다른 Service를 주입** | 비즈니스 로직을 Service 단위로 재사용 | 주입이 얽히다 보면 순환 참조 위험 |
| **3. Facade Service로 조합** 👍 | 순환 참조 해결, 트랜잭션을 한 곳에서 관리, 각 Service는 자기 도메인만 | 클래스가 늘어 작은 프로젝트에선 과할 수 있음 |

![Facade Service](oop-4-facade.png)

```java
@Service
@RequiredArgsConstructor
public class CreatePostService {
    private final PostService postService;
    private final MemberService memberService;
    private final BoardService boardService;

    @Transactional
    public PostResponseDto createPost(PostRequestDto dto, String username) {
        Board board = boardService.findById(dto.getBoardId());
        Member member = memberService.findByEmail(username);
        return postService.save(dto.toEntity(board, member)).toResponseDto();
    }
}
```

이것도 정답은 없어요. 서비스 성격에 맞게 팀원들과 합의해서 정하면 됩니다.

## 아키텍처에도 객체지향을 적용할 수 있다

지금까지는 코드 수준이었는데, 사실 **패키지와 모듈 수준**에서도 같은 고민을 할 수 있어요. 먼저 우리가 익숙한 구조부터 봅시다. 모앤디의 패키지 구조예요.

![모앤디 domain 패키지](moandi-domain-tree.png){: width="220" .normal }
![모앤디 global 패키지](moandi-global-tree.png){: width="240" .normal }

도메인마다 `controller / dto / entity / repository / service`가 묶여 있는 구조, 다들 한 번씩은 써 봤을 거예요. 이게 **계층형 아키텍처(Layered Architecture)**입니다. 잘 만들면 계층마다 독립적이라 구현을 바꾸기 쉬워요. 그런데 정말 완벽할까요?

![계층형 아키텍처](oop-3-layered.png)

### 계층형 아키텍처의 네 가지 구조적 문제

**1. DB 중심 설계를 유도한다**

Entity를 만들 때 보통 "ERD 짜고 → 테이블 잡고 → Entity 만들고 → Service 짜고" 순서로 가죠. 애플리케이션의 목적은 비즈니스 규칙을 모델링하는 건데, DB 구조를 먼저 정하고 도메인 로직을 거기에 끼워 맞추게 돼요. JPA와 만나면 `@Entity`가 모든 것의 중심이 됩니다.

```java
@Entity
public class Recruitment {
    @ManyToOne(fetch = FetchType.LAZY)
    private Designer designer;

    @OneToMany(cascade = CascadeType.ALL)
    private List<RecruitmentImage> images;
}
```

그러면 DB 스키마가 바뀔 때 도메인도 바뀌어야 하고, 도메인 로직을 손대고 싶어도 JPA 설정과 엮여 쉽게 못 건드려요. 코드를 잘못 짜서가 아니라 **구조가 이런 코드를 자연스럽게 유도**하는 거예요.

**2. 지름길을 택하기 쉽다**

규칙은 "위에서 아래로만 의존"인데, 마감이 다가오면 귀찮아서 이렇게 되기 쉽죠.

```java
@RestController
class OrderController {
    private final OrderRepository orderRepository;  // Controller가 Repository를 직접

    @PatchMapping("/orders/{id}/cancel")
    public void cancelOrder(@PathVariable Long id) {
        Order order = orderRepository.findById(id).orElseThrow();
        order.setStatus(OrderStatus.CANCELLED);     // 도메인 로직이 Controller에!
        orderRepository.save(order);
    }
}
```

**3. 유스케이스가 숨어 버린다**

한 Service가 몇 개의 유스케이스를 맡을지 제약이 없어서, 시간이 지나면 이렇게 됩니다.

```text
RecruitmentService.java
├── createRecruitment()    공고 생성
├── updateRecruitment()    공고 수정
├── closeRecruitment()     공고 마감
├── getApplicants()        지원자 조회
├── approveApplicant()     지원자 승인
└── ... 800줄 예상
```

공고 생성 로직이 어디 있는지 찾기 어렵고, 의존성이 많아 테스트도 힘들어져요. `CreateRecruitmentService`처럼 **유스케이스 단위로 좁힌 서비스**를 두면 훨씬 수월해집니다.

**4. 동시 작업이 어렵다**

새 유스케이스를 개발자 3명이 웹·도메인·영속성으로 나눠 동시에 만들 수 있을까요? 계층형에서는 Repository → Service → Controller 순으로 쌓아야 해서 어려워요. 넓은 Service 하나를 여럿이 고치면 머지 충돌도 잦고요. 인터페이스를 먼저 정의하면 나눠서 작업할 수 있지만, 그것도 DB 중심 설계를 피했을 때의 이야기입니다.

결국 핵심은 **개발자가 규칙을 의식적으로 지켜야 하는데, 그걸 강제하는 장치가 없다**는 거예요.

## 헥사고날 아키텍처

그 장치가 되어 주는 구조 중 하나가 **헥사고날 아키텍처(포트와 어댑터)**입니다.

![헥사고날 아키텍처](oop-5-hexagonal.png)

- **도메인**이 가운데에 있고, 어떤 기술에도 의존하지 않는다.
- 바깥과는 **포트(인터페이스)**로만 만난다. 들어오는 쪽은 UseCase, 나가는 쪽은 Repository 같은 출력 포트.
- Web, JPA, 외부 API는 포트를 구현한 **어댑터**일 뿐이라 갈아 끼울 수 있다.

1편의 DIP를 아키텍처 전체로 넓힌 셈이에요. 물론 장단점이 있습니다.

| 장점 | 단점 |
| --- | --- |
| 기술 교체가 쉽다 | 클래스·파일 수가 많아진다 |
| 테스트가 쉽다 | 계층마다 DTO 변환 코드가 필요하다 |
| 도메인 로직이 명확하다 | 초기 설계 비용이 크다 |

모든 프로젝트에 정답인 구조는 없으니, 장단점을 따져 각자 프로젝트에 맞게 적용하면 될 것 같아요.

## 발표를 준비하며 고민한 질문들

발표 전에 "이런 질문이 나오면 어떻게 답할까?"를 미리 정리해 봤어요. 정답이 하나로 정해진 질문들은 아니라서, 읽으면서 같이 고민해 보시면 좋겠습니다.

- **KISS와 객체지향 설계가 충돌할 때는 없을까?** 메서드를 쪼개고 인터페이스를 만들면 파일 수가 늘어나는데, 그게 정말 "Simple"한 걸까?
- **모든 로직을 Entity로 옮기면 Entity가 너무 커지지 않을까?** Service의 비대함을 Entity로 옮겨 놓은 것뿐이라면?
- **구현체가 하나뿐인데도 인터페이스를 만드는 건 YAGNI 위반 아닐까?** 확장 가능성과 과잉 설계 사이의 기준은?
- **Facade Service도 결국 또 다른 Fat Service가 되지 않을까?**
