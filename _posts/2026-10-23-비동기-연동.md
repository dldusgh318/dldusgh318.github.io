## 동기 연동과 비동기 연동

**동기 방식**은 한 작업이 끝나야 다음 작업이 진행된다. 코드 순서가 곧 실행 순서라서 흐름을 이해하기 쉽고 디버깅도 편하다.

그런데 외부 연동이 끼어들면 따져 볼 게 생긴다.

1. 외부 연동이 실패하면 **전체 기능도 실패**해야 하는가?
2. 연동하는 서비스의 **응답 시간**은 얼마나 되는가?
3. 다음 작업에 외부 연동의 **결과가 필요**한가?

결과가 필요 없고, 응답이 느리거나, 연동 실패가 전체 로직을 망치게 두고 싶지 않다면 **비동기 연동**을 고려해 보자.

![동기 연동 흐름](05-1-sync.png)
_동기: 포인트 서비스가 느리면 로그인도 같이 느려진다_

![비동기 연동 흐름](05-2-async.png)
_비동기: 포인트 지급은 별도 스레드에 맡기고 로그인은 바로 응답_

비동기 연동이 잘 맞는 예시는 이런 것들이다.

- 주문이 들어오면 판매자에게 푸시 알림
- 결제 후 포인트 지급
- 콘텐츠 등록 시 검색 서비스에도 등록
- 인증 번호 SMS 발송

공통점은 다음과 같다.

1. 약간의 시차가 생겨도 괜찮다.
2. 실패해도 재시도할 수 있다.
3. 실패하면 나중에 수동으로 처리할 수 있다.
4. 실패해도 무시해도 되는 경우가 있다.

비동기 연동에는 여러 방법이 있다. 하나씩 보자.

## 별도 스레드로 실행하기

가장 쉬운 방법이다. 연동 작업을 새 스레드에서 실행하거나, 매번 만드는 대신 **스레드 풀**에 맡긴다. Spring이라면 `@Async`로 간단히 구현할 수 있다. 이때 메서드 이름만 봐도 비동기라는 걸 알 수 있게 짓자.

> 별도 스레드에서 터진 예외는 호출한 쪽의 try-catch로 잡히지 않는다. 비동기로 실행되는 코드는 **내부에서 직접 오류를 처리**해야 한다.
{: .prompt-warning }

### 스레드와 메모리

스레드는 각자 일정량의 메모리를 쓰고, 만드는 데 시간도 걸린다. 스레드 풀을 쓰면 개수가 고정되니 메모리 사용량이 일정하고 생성 비용도 줄어든다. 대신 풀 크기보다 작업이 많으면 나머지는 대기한다.

네트워크 I/O처럼 기다리는 시간이 긴 작업이라면 Java의 **가상 스레드**나 Go의 **고루틴**을 고려하자. OS 스레드가 아니라 런타임이 관리하는 경량 스레드라서 메모리를 훨씬 적게 쓴다.

## 메시징

![메시징 시스템을 이용한 연동](05-3-messaging.png)

시스템 A가 보낸 메시지를 메시징 시스템이 받아 시스템 B에 전달한다. 구조가 하나 더 생기는데도 쓰는 이유는 두 가지다.

1. **서로 영향을 덜 준다.** A의 트래픽이 늘어 B의 처리량을 넘더라도, 메시징 시스템이 B의 속도에 맞춰 전달하니 B가 무너지지 않고 A도 덜 흔들린다.
2. **확장이 쉽다.** A의 데이터를 C도 받아야 한다면, A의 코드를 고치지 않고 C를 메시징 시스템에 연결하기만 하면 된다.

![소비자를 붙여 확장](05-4-fanout.png)

- **생산자(게시자)**: 메시지를 만들어 메시징 시스템에 보내는 쪽
- **소비자(구독자)**: 메시징 시스템에서 메시지를 받아 처리하는 쪽

대표적인 도구로는 Kafka, RabbitMQ, Redis Pub/Sub이 있고, 책에서는 각각의 특징과 어울리는 상황도 비교한다.

### 생산자 쪽: 유실을 막자

메시지를 보내다 타임아웃이 났는데 그냥 무시하면 메시지는 사라진다. 유실되면 안 되는 메시지라면 **재시도**하거나 **실패 로그를 남겨** 나중에 후처리할 수 있게 하자.

### 소비자 쪽: 중복을 대비하자

소비자는 같은 메시지를 두 번 처리할 수 있다.

- 생산자가 같은 내용의 메시지를 두 번 보낸 경우 → 메시지마다 **고유 ID**를 붙이고, 처리한 ID를 DB나 메모리에 기록해 걸러 낸다.
- 처리 중 오류로 같은 메시지를 다시 받은 경우 → 처리 로직 자체를 **멱등**하게 만든다.

그리고 소비가 잘 되고 있는지 **모니터링**하자. 큐가 가득 차면 새 메시지를 넣지 못해 문제가 커진다.

### 이벤트와 커맨드

| 종류 | 의미 | 수신자 | 예시 |
| --- | --- | --- | --- |
| **이벤트** | 어떤 일이 일어났다 | 정해져 있지 않음 → 확장이 쉬움 | 주문 완료, 배송 완료, 로그인 실패 |
| **커맨드** | 무언가를 해 달라 | 특정 기능 실행이 목적 | 포인트 지급, 배송 완료 문자 발송 |

> **궁극적 일관성**: 두 저장소의 데이터가 결국에는 맞춰지지만, 즉시는 아니다. 그 사이에는 잠깐 불일치가 생길 수 있다. 비동기 메시징도 이런 성격을 갖는다.
{: .prompt-tip }

## 트랜잭션 아웃박스 패턴

메시징을 열심히 구축해도, DB 저장은 성공했는데 메시지 발행이 실패하면 소용이 없다. 그래서 **메시지를 먼저 DB에 안전하게 저장**해 두는 방법이 아웃박스 패턴이다.

1. 업무 데이터 변경과 **아웃박스 테이블에 메시지 INSERT**를 **한 트랜잭션**으로 묶는다.
2. 별도의 메시지 중계기가 아웃박스에서 아직 보내지 않은 메시지를 읽어 전송한다.

![트랜잭션 아웃박스 패턴](05-5-outbox.png)

중계기는 대략 이렇게 주기적으로 돈다.

```java
// 주기적으로 호출돼서 아웃박스에 쌓인 메시지를 보낸다
public void relayOutbox() {
    // 아직 안 보낸(WAITING) 메시지를 쌓인 순서대로 가져온다
    List<OutboxMessage> pending = outboxRepository.findWaitingOrderById();

    for (OutboxMessage msg : pending) {
        try {
            messageSender.send(msg);                 // 메시징 시스템으로 전송
            outboxRepository.markDone(msg.getId());  // 보냈으면 DONE 표시
        } catch (Exception e) {
            outboxRepository.recordFailure(msg.getId(), e); // 실패 기록 (failCount++)
            break; // 순서를 지키기 위해 여기서 멈춘다
        }
    }
}
```

실패하면 루프를 멈추는 이유는 **메시지 순서**를 지키기 위해서다. 순서가 중요하지 않다면 건너뛰고 계속 보내도 된다.

보낸 메시지를 표시하는 방법은 두 가지다.

- 아웃박스 테이블에 **상태 컬럼**(대기, 완료, 실패)을 둔다.
- 마지막으로 보낸 **메시지 ID를 따로 기록**한다. 책에서는 여러 중계기가 한 아웃박스 테이블을 함께 쓰는 환경이라면 이쪽이 낫다고 설명한다.

### 아웃박스 테이블 구조

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | BIGINT | PK. 저장 순서대로 증가하는 값 |
| `messageId` | VARCHAR | 메시지 고유 ID |
| `messageType` | VARCHAR | 메시지 타입 |
| `payload` | CLOB | 메시지 데이터 (JSON, XML 등) |
| `status` | VARCHAR | `WAITING`, `DONE`, `FAILED` |
| `failCount` | INT | 실패 횟수 |
| `occurredAt` | TIMESTAMP | 메시지 발생 시간 |
| `processedAt` | TIMESTAMP | 처리 시간 |
| `failedAt` | TIMESTAMP | 마지막 실패 시간 |

기본 틀일 뿐이니 상황에 맞게 바꿔 쓰면 된다. 어떤 기준으로 `FAILED`를 줄지, 그 뒤엔 어떻게 처리할지도 같이 정하자. 수동 처리를 위해 `EXCLUDED`(제외) 같은 상태를 더 두기도 한다.

## 배치 전송

데이터를 비동기로 연동하는 전통적인 방법이다. 메시징이 거의 실시간이라면, 배치는 **일정 간격**으로 모아서 보낸다.

1. DB에서 보낼 데이터를 조회한다.
2. 결과를 파일로 기록한다.
3. FTP, SFTP, SCP 등으로 파일을 연동 시스템에 보낸다.

파일 형식, 주고받는 시간, 경로, 그리고 **누가 전송을 맡을지**(생산자가 업로드할지, 소비자가 다운로드할지)를 미리 합의해야 한다. 같은 조직 안이라면 **읽기 전용 DB 계정을 열어 주는 방식**도 쓴다.

전송 실패를 대비해 **일정 시간 뒤 재전송**하는 기능을 만들고, 그래도 실패할 때를 위해 **수동으로 배치를 다시 돌릴 수 있는 명령이나 API**도 준비해 두자.

## CDC (Change Data Capture)

**변경된 데이터를 추적해서, 그 변경분으로 다른 작업을 할 수 있게 해 주는 패턴**이다. Oracle이나 MySQL 같은 DB는 데이터가 바뀌면 그 내용을 알려 주는 기능이 있는데(MySQL이라면 바이너리 로그), CDC는 이걸 활용한다.

![CDC 처리 흐름](05-6-cdc-flow.png)

변경 데이터는 레코드 단위로 넘어오고, 추가·수정·삭제를 구분하는 플래그가 함께 온다. CDC 처리기는 이걸 대상 시스템에 두 가지 방식으로 전파한다.

**1. 그대로 전파**: 원본과 대상 데이터가 1:1 관계일 때 알맞다.

![그대로 전파](05-7-cdc-copy.png)

**2. 가공해서 전파**: 필요한 변경만 골라 의미 있는 형태로 보낸다. 새 주문이 들어온 변경과 주문 상태가 '배송중'으로 바뀐 변경이 함께 왔다면, 알림 시스템에는 후자만 `(주문 ID, 상태)`로 보내면 된다.

![가공해서 전파](05-8-cdc-transform.png)

전파 대상은 DB, 메시징 시스템, API 등 목적에 따라 다양하게 둘 수 있다.

> **CDC와 이벤트는 다르다.** CDC는 "member 테이블의 name 컬럼이 바뀌었다"까지는 알려 주지만, 그게 "회원이 닉네임을 바꿨다"인지 "관리자가 수정했다"인지는 알려 주지 않는다. 비즈니스 의미가 필요하다면 이벤트가 맞다.
{: .prompt-tip }

### 처리 위치를 반드시 기록하자

CDC 처리기는 **어디까지 읽었는지(위치)**를 꼭 기록해야 한다. MySQL 바이너리 로그의 각 항목에는 로그 파일 안에서의 위치 값이 있다. 이걸 저장해 두면 처리기가 재시작해도 마지막으로 읽은 곳부터 이어서 읽는다.

기록하지 않으면 재시작 후 최신 로그부터 읽게 되고, **재시작하는 동안 생긴 변경은 그대로 놓친다.**

### CDC가 빛나는 순간

연동 코드를 넣기 부담스러울 때 CDC가 유용하다. 책의 사례에서는 주문 시스템을 새로 만들면서 신규 주문 데이터를 기존 주문 시스템에도 반영해야 했는데, 신규 시스템 팀은 일정도 빠듯하고 코드도 이미 복잡해서 연동 코드 추가를 꺼렸다. 그래서 CDC를 택했다.

![CDC 활용 사례](05-9-cdc-case.png)

- 신규 시스템 코드는 건드리지 않고 다른 시스템에 데이터를 전파했다.
- 연동 대상이 둘이고 처리 속도도 달라서 중간에 Kafka를 두었다.
- 덕분에 신규 시스템의 개발 일정에 주는 영향을 최소화했다.

## 그래서 언제 무엇을 쓸까

책을 읽고 나서 "CDC가 코드 수정 없이 모든 변경을 잡는다면, 왜 다른 방식을 다 대체하지 못할까?"가 궁금해서 따로 정리해 봤다.

| 방식 | 이럴 때 | 이럴 땐 X |
| --- | --- | --- |
| **별도 스레드** | 유실돼도 괜찮은 가벼운 작업 (알림, 로그) | 서버가 죽으면 사라지면 안 되는 작업 |
| **메시징** | 다른 서비스에 "사건"을 알려야 할 때 (주문 완료 → 포인트, 배송) | 수신자가 하나뿐이고 단순할 때 |
| **배치** | 실시간이 필요 없고 양이 많을 때 (정산, 외부 기관 파일 연동) | 몇 초 안에 반영돼야 할 때 |
| **CDC** | 데이터를 **그대로 복제**할 때 (검색 엔진, 분석 DB, 캐시) | 비즈니스 의미를 전달해야 할 때 |

변경을 잡아내는 방식만 놓고 보면 이렇게 나뉜다.

| 방식 | 동작 | 장점 | 부담 |
| --- | --- | --- | --- |
| 전체 배치 복사 | 주기적으로 통째로 가져옴 | 단순함 | 많이 읽고 반영이 늦음 |
| 증분 폴링 | `updated_at > 마지막 수집 시각`으로 조회 | 구현이 쉬움 | 삭제 감지와 경계 시각 처리가 까다로움 |
| DB 트리거 | 변경 시 이력 테이블에 기록 | DB 안에서 포착 | 쓰기 경로에 부담이 더해짐 |
| 저장 후 메시지 발행 | 저장 뒤 `주문완료` 같은 메시지 전송 | 의미를 정확히 표현 | 저장과 발행 중 하나만 성공할 수 있음 |
| 트랜잭션 아웃박스 | 데이터와 이벤트를 한 트랜잭션에 저장 | 저장·발행 불일치 해결 | 중계기와 중복 처리가 필요 |
| 로그 기반 CDC | DB 변경 로그를 읽어 전달 | 앱 수정이 적고 변경분만 수집 | 로그 보관, 권한, 스키마 변경, 재처리 관리 |

CDC의 한계도 분명하다.

- 변경의 **의미**를 알 수 없다.
- 내 테이블 구조가 사실상 **남의 API**가 된다. 스키마를 바꾸면 소비하는 쪽이 깨진다.
- CDC가 멈추면 로그가 쌓여 **원본 DB가 위험**해질 수 있다.
- 운영 부담이 크고, 개인정보가 의도치 않게 흘러갈 수 있으며, **중복**도 여전히 생긴다.

## 비동기로 돌아가는 세상

생각해 보면 세상은 동기보다 비동기에 가깝다. 메일을 받자마자 답장하지 않고, 업무 메시지를 받아도 하던 일을 마치고 처리하고, 카페는 주문 여러 개를 모아 한 번에 만든다.

시스템 연동도 그렇다. 생각보다 많은 연동이 비동기여도 괜찮다. 물론 구조가 복잡해지고 데이터가 잠깐 어긋나는 시기도 생기지만, 성능·안정성·자율성 면에서 얻는 게 있다.

모든 연동을 비동기로 할 필요는 없다. **복잡도가 늘어나는 것보다 얻는 이점이 더 클 때** 선택하자.

## 정리하며

예전에 분석 요청을 `AFTER_COMMIT` 이후 Executor로 넘겨 비동기 처리하는 구조를 직접 실험해 본 적이 있다. 사용자 응답은 확실히 빨라졌지만, 큐가 가득 차면 요청이 거절된 채 `PENDING`으로 남고, 서버가 재시작되면 메모리 큐의 작업은 복구되지 않았다. 그때 다음 단계로 고민했던 게 바로 이 장의 **아웃박스 패턴**이었다. "비동기로 분리하면 대기가 사라지는 게 아니라 위치가 옮겨 갈 뿐이고, 전달 보장은 별개의 문제"라는 걸 책으로 다시 한번 정리할 수 있었다.
