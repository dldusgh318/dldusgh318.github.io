## 들어가기 전..

여러분, 서버에 성능 문제가 생겼을 때 가장 먼저 떠오르는 해결책은 뭔가요?

보통 DB 서버를 수직 확장하거나 수평 확장하는 걸 떠올리실 거예요.

**그런데 서버 확장은 처리량(Throughput)만 늘려 줄 뿐, 응답 시간(Latency)은 크게 줄여 주지 못합니다.**

요청을 더 많이 받을 수 있게 될 뿐, 쿼리 자체가 빨라지는 건 아니니까요! 게다가 DB 서버를 확장하면 비용도 많이 들죠.

그렇다면, DB 서버를 확장하지 않고도 응답 시간과 처리량을 개선하려면 어떻게 해야 할까요?

⇒ **캐시**를 쓰면 됩니다!!

오늘은 캐시가 무엇인지, 그리고 어떻게 쓰는 건지 알아보겠습니다 ㅎㅎ

## 캐시란 무엇인가

: 자주 사용하는 데이터나 값을 미리 복사해 두는 임시 저장소

캐시에 데이터를 저장해 두면, 같은 데이터를 요청할 때 DB가 아닌 캐시에서 읽어 와 응답할 수 있습니다.

![캐시 개념](cache-01-concept.png)

일반적으로 캐시에서 읽는 속도가 DB보다 빠르기 때문에, 자주 조회되는 데이터를 캐시에 보관하면 응답 시간을 줄일 수 있어요.

<details markdown="1">
<summary>왜 캐시가 DB보다 읽는 속도가 빠른가요?</summary>

![캐시가 빠른 이유](cache-02-speed.png)

```text
DB 조회:   네트워크 왕복 + 디스크 I/O + 쿼리 실행  ≈ 수십 ms
캐시 조회: 네트워크 왕복 + 메모리 읽기            ≈ 1ms 이하
```

DB는 데이터를 디스크에 저장하기 때문에 디스크 I/O가 발생합니다. 반면 캐시는 메모리에 데이터를 올려 두기 때문에 훨씬 빠르죠.

</details>

```text
캐시 키 예시
"posts:1"    → { id: 1, title: "캐시란 무엇인가", ... }
"posts:hot"  → [{ id: 5, ... }, { id: 3, ... }]
```

> 캐시 키는 충돌 없이 고유하게 설계하는 게 중요합니다!! `posts:1`처럼 `도메인:식별자` 형태가 일반적이에요.
{: .prompt-tip }

## 캐시 전략

그렇다면 무작정 캐시를 쓰는 게 좋을까요?

→ **안 됩니다!!** 캐시는 메모리 기반이라 저장 공간이 DB보다 훨씬 작아요. 아무 데이터나 다 넣으면 금방 꽉 차 버리고, 정작 중요한 데이터를 못 넣는 상황이 생깁니다.

또 캐시를 쓰면 **데이터 정합성 문제**가 생길 수도 있어요.

> ex) DB 데이터는 바뀌었는데 캐시는 예전 데이터를 들고 있는 경우

그래서 기준을 잡고 어떤 데이터를 캐싱할지 판단해야 합니다.

### 캐시 도입의 판단 기준

| 기준 | 질문 | 예시 |
| --- | --- | --- |
| **Read-heavy** | 읽기가 쓰기보다 압도적으로 많은가? | 게시글 상세 조회 |
| **Slow I/O** | DB 조회나 계산 비용이 비싼가? | 복잡한 통계 쿼리, 외부 API |
| **Low Volatility** | 데이터가 자주 바뀌지 않는가? | 공지사항, 상품 카테고리 |
| **Repeatability** | 같은 요청이 반복적으로 오는가? | 인기 게시글, 메인 피드 |
| **Staleness 허용** | 1~2초 오래된 데이터여도 괜찮은가? | 조회수, 좋아요 수 |

즉 정리해 보자면,,

- ✅ 자주 조회되지만 값이 잘 변하지 않는 데이터 (by 파레토 법칙: 전체 데이터의 20%만 캐싱해도 요청의 80%를 커버할 수 있다)
- ✅ 계산 비용이나 조회 비용이 비싼 데이터

반대로 **실시간 정확성이 중요한 데이터**(재고, 잔액, 예약 현황)는 캐시 적용을 신중하게 해야 해요.

<details markdown="1">
<summary>왜 실시간 정확성이 중요한 데이터에는 캐시를 쓰면 안 될까요?</summary>

캐시는 기본적으로 **"약간 오래된 데이터를 빠르게 주는 것"**을 전제로 합니다.

ex) 재고가 10개 남았는데 캐시에는 50개로 남아 있다면?

→ 실제로는 품절인데 구매 버튼이 활성화되는 문제 발생..

</details>

그렇다면 판단 기준에 맞게 캐시를 도입한 뒤, 캐시를 잘 쓰고 있는지는 어떻게 알 수 있을까요?

→ **캐시 적중률(Cache Hit Ratio)**을 보면 됩니다!!

### 캐시 적중률 (Cache Hit Ratio)

```text
캐시 적중률 = 캐시에서 응답한 건수 / 전체 조회 요청 건수
```

적중률이 높을수록 DB 부하가 줄고 응답 시간이 빨라지는데요, 일반적으로 80% 이상이면 잘 쓰고 있는 걸로 봅니다.

반대로 **적중률이 낮으면 캐시는 오히려 독**이 됩니다. 캐시를 거쳐서 DB까지 가는 경로가 하나 더 생기니까, 없는 것보다 느려질 수 있어용

적중률을 올리는 방법은 세 가지예요.

1. **캐시 대상을 잘 고른다**: 자주 조회되는 데이터 위주로
2. **TTL을 적절히 설정한다**: 너무 짧으면 캐시 미스가 잦고, 너무 길면 오래된 데이터가 남는다
3. **캐시 사전 적재(Cache Warming)**: 트래픽이 몰리기 전에 미리 데이터를 올려 두기
   ex) 매달 1일에 푸시 알림을 보내고 요금 정보 조회가 몰리는 서비스라면, 알림 보내기 전에 미리 캐시에 올려 두기!

<details markdown="1">
<summary>그럼 TTL은 어떻게 설정하는 게 좋나요?</summary>

| 데이터 유형 | 권장 TTL | 이유 |
| --- | --- | --- |
| 실시간 데이터 (주식, 위치) | 1초 ~ 10초 | 데이터 일관성 극대화 |
| 인기·트렌드 (인기 게시물) | 1분 ~ 5분 | 최신 트렌드 반영 + 부하 분산 |
| 사용자 프로필·세션 | 10분 ~ 1시간 | 적절한 일관성과 조회 성능 |
| 정적 콘텐츠 (이미지, CSS) | 1일 ~ 1개월 | 변경 가능성 낮음 |

**TTL 결정 체크리스트**

- 이 데이터가 바뀌는 주기가 얼마인가?
- 오래된 데이터가 노출되면 어떤 비즈니스 문제가 생기나?
- 캐시 미스가 났을 때 DB가 그 부하를 감당할 수 있나?

</details>

### 캐시 읽기·쓰기 전략

캐시에는 여러 개의 읽기 전략, 쓰기 전략이 있다는 거 아시나요? 어떤 전략을 쓰느냐에 따라 성능과 정합성이 달라지기 때문에, 상황에 맞는 걸 고르는 게 중요해요. 하나씩 알아봅시다!

#### Look-Aside (= Lazy Loading)

캐시를 먼저 조회하고, 데이터가 없으면 DB에서 조회해서 캐시에 쓰는 전략이에요.

![Look-Aside](cache-03-look-aside.png)

1. 캐시 먼저 조회
2. 있으면 (Cache Hit) → 캐시에서 데이터 가져오기
   없으면 (Cache Miss) → DB에서 조회한 뒤 캐시에 write

```java
public Post getPost(Long id) {
    Post cached = cache.get("posts:" + id);
    if (cached != null) return cached;          // 캐시 히트

    Post post = postRepository.findById(id);    // 캐시 미스 → DB 조회
    cache.set("posts:" + id, post, TTL_10MIN);  // 캐시에 저장
    return post;
}
```

**장점 👍**
- 요청이 온 데이터만 캐싱 → 메모리 낭비 없음
- 캐시 미스가 나도 DB에서 가져오니까 서비스는 정상 동작

**단점 👎**
- 첫 요청은 항상 DB까지 간다 (Cold Start 문제)
- Redis가 다운되거나 DB에만 새 데이터가 있으면 Cache Miss가 대량으로 나서 DB에 순간적으로 부하가 몰린다
  → **Cache Warming**으로 해결할 수 있어요

#### Read-Through

캐시에서만 조회하고, Cache Miss가 나면 **캐시 레이어가 직접** DB에서 읽어 와 캐시에 저장한 뒤 반환하는 전략이에요.

![Read-Through](cache-04-read-through.png)

✅ Look-Aside와 흐름은 비슷하지만, DB 조회 로직이 **애플리케이션 코드가 아니라 캐시 레이어 안**에 있다는 점!

#### Write-Around (DB에만 저장)

모든 데이터는 DB에 저장해 두고, Cache Miss가 났을 때만 캐시에 올리는 전략이에요. 읽기는 Look-Aside나 Read-Through와 같이 씁니다.

![Write-Around](cache-05-write-around.png)

**장점 👍**
- 쓰기가 빠르다
- 한 번도 안 읽힐 데이터는 캐시에 안 올라감 → 메모리 효율적

**단점 👎**
- 데이터가 바뀐 직후에 캐시에 예전 값이 남아 있으면, 그동안은 데이터 불일치 발생

#### Write-Through (동시 저장)

데이터를 캐시와 DB에 동시에 저장하는 전략이에요.

![Write-Through](cache-06-write-through.png)

**장점 👍**
- 캐시와 DB가 항상 일치 → 정합성이 중요한 데이터에 적합하겠죵?

**단점 👎**
- 쓰기 응답 시간이 늘어난다 (캐시 + DB 두 군데에 write)
- 한 번도 안 읽힐 데이터까지 캐시에 올라갈 수 있다
- **⚠️ 캐시에 먼저 쓰고 DB에 쓰다가 실패하면 데이터 불일치 발생**

```java
cache.set(key, post);      // 1. 캐시 저장 성공
repository.save(post);     // 2. DB 저장 실패 → 캐시에는 있고 DB에는 없는 상태
```

그래서 실무에서는 Write-Through보다 **"DB 먼저 저장 + AFTER_COMMIT 후 캐시 갱신"** 패턴을 많이 쓴다고 해요.

#### Write-Back

데이터를 캐시에 먼저 저장하고, 나중에 비동기로 특정 시점에 DB에 저장하는 전략이에요.

![Write-Back](cache-07-write-back.png)

**장점 👍**
- 쓰기 성능이 가장 빠르다
- write를 모아서 한 번에 처리하니까 DB 부하를 크게 줄일 수 있다

**단점 👎**
- **캐시가 날아가면 DB에 반영 안 된 데이터는 유실**
  → 그래서 주로 로그, 집계 데이터처럼 약간의 유실은 감수할 수 있는 경우에 씁니당

### 💬 추가로 고민해 볼 점: 캐시를 업데이트할 땐 갱신? 삭제?

- **갱신 (Update)**: 새 데이터로 캐시를 업데이트
- **삭제 (Evict)**: 캐시를 그냥 지우고, 다음 읽기 요청이 오면 DB에서 새로 가져오기

→ **삭제하는 게 좋습니다.**

여러 서버가 동시에 같은 데이터를 수정하는 경우를 생각해 봅시다.

```text
서버 A: DB 업데이트 → 캐시에 새 값 저장 (T+1)
서버 B: DB 업데이트 → 캐시에 새 값 저장 (T+2)
```

타이밍이 엇갈리면 오래된 값이 최신 값을 덮어쓰는 **Race Condition**이 발생합니다.

**반면** 삭제 방식은 그냥 캐시에서 지워 버리니까, 다음 요청에서 DB의 정확한 최신 값을 가져와서 단순해요.

```java
@CacheEvict(value = "posts", key = "#postId")   // 캐시는 그냥 지워 버리깅
public void updatePost(Long postId, UpdateRequest req) {
    postRepository.update(postId, req);          // DB 업데이트
}
```

<details markdown="1">
<summary>💡 여기서 잠깐!! 삭제 타이밍도 중요합니다</summary>

```text
[문제 상황]
A 스레드: DB 업데이트 시작 (아직 Commit 전)
A 스레드: 캐시 Evict (Commit 전에 삭제!)
B 스레드: Cache Miss → DB 조회 → ⚠️ 아직 Commit 안 된 이전 데이터를 캐시에 적재
A 스레드: DB Commit 완료 → 하지만 캐시에는 이미 이전 데이터가 올라간 상태
```

그래서 **DB에 Commit된 이후에 캐시가 삭제**되도록 타이밍을 맞춰야 해요. Spring에서는 `@TransactionalEventListener(phase = AFTER_COMMIT)`으로 해결할 수 있습니다.

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onTermsUpdated(TermsUpdatedEvent event) {
    // DB Commit 이후에 캐시 삭제 → 이전 데이터가 다시 올라가는 문제 방지
    cache.evict("terms:" + event.getTermsId());
}
```

단, `AFTER_COMMIT` 방식은 캐시 Evict가 실패해도 이미 Commit된 상태라 롤백이 안 돼요.. → 데이터 불일치

✅ solution: 재시도 + 짧은 TTL 조합

```java
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Retryable(value = RedisConnectionException.class, maxAttempts = 3,
           backoff = @Backoff(delay = 100))
public void onPostUpdated(PostUpdatedEvent event) {
    cacheManager.getCache("posts").evict(event.getPostId());
}
// + TTL을 짧게 잡아 두면 Evict가 실패해도 TTL 만료 때 자동으로 정합성 회복
```

</details>

### 캐시 삭제 정책

캐시는 메모리 기반이라 용량 한계가 있는데요, **꽉 찼을 때 뭘 지울지 결정**하는 게 삭제 정책이에요!

| 정책 | 설명 | 적합한 상황 |
| --- | --- | --- |
| **LRU** (Least Recently Used) | 가장 오래전에 사용된 것부터 삭제 | 일반적인 캐시에 가장 많이 씀 |
| **LFU** (Least Frequently Used) | 사용 빈도가 가장 낮은 것부터 삭제 | 인기 콘텐츠가 명확한 경우 |
| **FIFO** | 먼저 들어온 것부터 삭제 | 단순 큐 형태 캐시 |

Redis에서는 `maxmemory-policy`로 이 정책을 지정하는데, 가장 많이 쓰는 건 `allkeys-lru`예요.

## 캐시… 잘못 쓰면 독이 된다?

캐시를 잘못 운영하면 오히려 서비스를 망칠 수 있습니다.. 제일 많이 만나는 문제들을 볼게요.

### Cache Avalanche

: **대량의 캐시 키가 동시에 만료돼서, 모든 요청이 한꺼번에 DB로 쏟아지는 현상**이에요. 주로 캐시가 전부 같은 시간에 만료되도록 구현하면 생기는 문제지용

![Cache Avalanche](cache-08-avalanche.png)

```text
[상황]
비슷한 시간에 저장된 캐시 키들이 TTL 10분으로 설정됨
→ 10분 뒤 전부 동시에 만료
→ 갑자기 수천 개의 요청이 DB로 직행
→ DB 과부하
```

**✅ solution: TTL에 랜덤 값(Jitter)을 더해서 만료 시간을 흩뿌리자!**

```java
// ❌ 모든 게시글 캐시 TTL이 정확히 10분 → cache avalanche 발생..
cache.set("posts:" + id, post, Duration.ofMinutes(10));

// ✅ 10분 + 최대 2분 랜덤
long jitter = ThreadLocalRandom.current().nextLong(120);
cache.set("posts:" + id, post, Duration.ofSeconds(600 + jitter));
```

### Cache Penetration

: **캐시에도 DB에도 없는 데이터를 반복해서 요청해서, 매번 DB까지 쿼리가 날아가는 현상**이에요.

![Cache Penetration](cache-09-penetration.png)

```text
[상황]
악의적인 요청자가 존재하지 않는 키(id=-1, id=9999999)를 반복 요청
→ 캐시 미스 → DB 조회 → DB에도 없음 → "없음" 반환
→ 이걸 계속 반복하면 DB 부하 증가..
```

"값이 없다"는 정보 자체를 캐싱하지 않으면 매번 DB까지 조회하게 돼요.

**✅ solution: 조회 결과가 없어도 `null`을 캐시에 저장하자! (Null Object Pattern)**

그러면 다음 요청부터는 캐시에서 null을 반환하고 DB는 안 건드려도 됩니다.

```java
Post post = postRepository.findById(id);   // null일 수도 있음
cache.set("posts:" + id, post, TTL_1MIN);  // null이어도 저장
```

단, TTL은 짧게 잡는 게 좋아요. 나중에 진짜 데이터가 생겼는데 오래된 null이 남아 있으면 안 되니까용

> 💡 **Bloom Filter**라는 방법도 있어요! 확률적으로 "이 키가 존재하는가"를 판단해서 아예 DB 조회를 막는 구조인데, 운영이 복잡해져서 대부분은 Null 캐싱으로 충분합니다. ([블룸 필터 참고](https://codingapple.com/blog/bloom-filter/))
{: .prompt-tip }

### Hot Key Problem

: **특정 키에 요청이 폭발적으로 몰려서, 그 Redis 노드 자체가 과부하에 걸리는 현상**이에요.

```text
[상황]
쇼미더머니 콘서트 티켓팅 오픈
→ "concert:smticket" 키에 초당 수만 건 요청 집중
→ 캐시에 데이터는 있음, 근데 그 Redis 노드가 요청을 못 버팀
→ Redis 응답 지연 → 전체 서비스 느려짐
```

Redis는 싱글 스레드라 더 치명적이에요. 명령을 **하나씩 순서대로** 처리하기 때문에, 특정 키에 요청이 폭주하면 그걸 처리하느라 다른 모든 요청이 줄을 서게 되거든요.

**✅ solution: 로컬 캐시를 앞에 두는 2-Tier 구조를 쓰자!**

```text
요청 → 로컬 캐시 확인
     → 있으면 바로 반환
     → 없으면 Redis 조회
```

([Redis Hot Key 문제 참고](https://edd.ad/posts/hot-key-redis-distributed-cache-performance-guide-korean))

### Cache Stampede

: Hot Key가 **만료된 직후**, 여러 요청이 동시에 DB를 쓸데없이 반복 조회하는 현상이에요.

![Cache Stampede](cache-10-stampede.png)

```text
[상황]
"concert:smticket" 키 TTL 만료
→ 동시에 수천 개 요청이 캐시 미스
→ 수천 개가 전부 DB 조회 시도
→ DB 과부하 + 캐시에 같은 데이터를 수천 번 씀
```

**✅ solution: 분산 락(Distributed Lock)으로 DB 조회를 한 번만 허용하자!**

```text
캐시 미스 발생
→ 락 획득 시도
→ 락 잡은 요청 하나만 DB 조회 후 캐시에 저장
→ 나머지는 락 풀릴 때까지 대기 → 이후 캐시에서 조회
```

### 캐시 시스템 장애

: 말 그대로 캐시 시스템에 장애가 나서 DB로 부하가 쏠리는 현상이에요.

![캐시 장애](cache-11-failure.png)

```text
[상황]
트래픽 많은 시간대에 Redis 장애 발생
→ 평소 캐시가 처리하던 요청이 전부 DB로
→ DB가 감당 못 하고 과부하
→ 캐시와 상관없는 기능까지 느려지거나 다운
```

**✅ solution: 핵심 기능과 부가 기능을 구분하고, 대체 로직을 준비하자**

✋ 부가 기능까지 전부 DB로 폴백하면 DB까지 같이 죽을 수 있어요.. **꼭 핵심 / 부가 기능을 구분합시다.**

| 기능 | 분류 | 캐시 장애 시 |
| --- | --- | --- |
| 로그인, 결제, 주문 조회 | 핵심 | DB 폴백 허용 |
| 인기 게시글, 추천 콘텐츠 | 부가 | 잠시 비활성화 or 대체 UI |

```java
public PostDto getPost(Long postId) {
    try {
        PostDto cached = redisCache.get("posts:" + postId);
        if (cached != null) return cached;
    } catch (RedisConnectionException e) {
        log.warn("Redis 연결 실패, DB로 폴백합니다. postId={}", postId);
        // Redis 없어도 서비스는 동작
    }
    return postRepository.findById(postId).map(PostDto::from).orElseThrow();
}
```

<details markdown="1">
<summary>Circuit Breaker로 자동화할 수 있다?</summary>

위 패턴을 메서드마다 try-catch로 구현하면 반복이 많아지죠.. `Resilience4j`의 `Circuit Breaker`를 쓰면 자동으로 처리할 수 있다고 하네요!

```yaml
resilience4j:
  circuitbreaker:
    instances:
      redisCache:
        failureRateThreshold: 50      # 실패율 50% 넘으면 Redis 차단
        waitDurationInOpenState: 10s  # 10초 뒤 회복 시도
```

```java
@CircuitBreaker(name = "redisCache", fallbackMethod = "getPostFromDb")
public PostDto getPost(Long postId) {
    return redisCache.get("posts:" + postId, PostDto.class);
}

// Redis 장애 시 자동으로 이 메서드 호출
public PostDto getPostFromDb(Long postId, Throwable t) {
    log.warn("Redis 장애로 DB 폴백. postId={}", postId);
    return postRepository.findById(postId).map(PostDto::from).orElseThrow();
}
```

</details>
