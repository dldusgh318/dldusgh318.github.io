## 성능의 핵심은 DB

가입자가 늘고 동시 접속이 몰리는 시간대가 되자 응답이 10초를 넘기는 서비스가 있었다. 원인은 DB였다. 사용자가 조금만 늘어도 DB CPU 사용률이 90%를 넘었고, 모든 쿼리와 서버 응답이 함께 느려졌다.

범인은 **풀 스캔**이었다. 호출 빈도가 높은 기능의 쿼리가 풀 스캔을 하고 있었고, 데이터가 쌓일수록 실행 시간이 늘어난 것이다.

> **풀 스캔**은 테이블의 모든 데이터를 순서대로 읽는 것이다. WHERE 조건에 맞는 인덱스가 없을 때 발생한다. 데이터가 적을 때는 티가 안 나지만, 많아지면 응답 시간이 급격히 늘어난다.
{: .prompt-tip }

DB는 연동하는 모든 서버의 성능에 영향을 준다. 그리고 쿼리가 느린 건 DB 자체보다 **DB를 잘못 써서** 생기는 경우가 많다.

## 조회 트래픽을 고려한 인덱스 설계

대부분의 시스템은 조회 비율이 높다. 그런데 같은 기능이라도 서비스 규모에 따라 트래픽은 완전히 다르다. 카테고리별 게시글 목록 조회를 예로 들어 보자.

```sql
select id, category, writerId, title, content
from article
where category = 10
order by id desc
limit 20, 10;
```

- **사내 공지 게시판**: 일주일에 1건씩 올라오면 1년에 52건이다. 직원 1,000명이 5분 안에 읽어도 초당 3~4건 수준이라 인덱스가 없어도 된다.
- **인기 커뮤니티**: 하루 5,000건씩 6년이면 1,000만 건이 쌓인다. 목록을 볼 때마다 1,000만 건을 비교하는 풀 스캔이 동시에 여러 개 돌면 DB CPU가 100%에 닿는다.

두 번째 경우라면 `category` 인덱스가 반드시 필요하다. **테이블을 설계할 때 조회 패턴과 트래픽 규모를 함께 봐야 하는 이유**다.

> `title like '%검색어%'` 같은 조건은 풀 스캔을 일으킨다. 검색 엔진(Elasticsearch 등)을 쓸 수 없다면 DB의 **전문(full-text) 검색 인덱스**를 고려하자.
{: .prompt-info }

### 단일 인덱스와 복합 인덱스

고객센터에서 특정 사용자의 일자별 활동 내역을 조회하는 상황을 보자.

- 하루 10만 명이 방문해 평균 5번씩 활동하면 하루에 50만 건이 쌓인다.
- 이때 `userId` 하나만으로는 부족하고, `(userId, activityDate)` **복합 인덱스**가 있어야 조회 성능이 유지된다.

> **커버링 인덱스**는 쿼리에 필요한 컬럼을 모두 담고 있는 인덱스다. 인덱스만 읽고 실제 데이터 페이지에는 접근하지 않으니 더 빠르다.
{: .prompt-tip }

### 선택도를 고려한 컬럼 선택

**선택도**는 컬럼에서 고유한 값의 비율이다. 고유한 값이 많을수록 인덱스 효율이 좋다. 성별(`gender`)보다 출생 연도(`birthyear`)가 인덱스로 더 낫다.

하지만 선택도가 낮다고 무조건 빼면 안 된다. 작업 큐에서 `status = 'W'`(대기)인 작업을 반복해서 꺼내는 쿼리라면, 대기 상태는 전체 중 일부라서 `status` 인덱스가 효과적이다. **어떤 값으로 자주 조회하는가**가 기준이다.

### 인덱스는 필요한 만큼만

인덱스에도 비용이 있다.

1. INSERT, UPDATE, DELETE 때마다 인덱스도 함께 관리해야 한다.
2. 인덱스도 데이터라서 메모리와 디스크를 차지한다.

같은 컬럼에 겹치는 인덱스를 또 만들지 않도록 주의하자.

## 인덱스 말고도 조회를 빠르게 하는 방법

### 미리 집계하기

설문 목록에 답변 수와 좋아요 수를 함께 보여 준다고 하자. 목록을 조회하면서 매번 `count(*)` 서브쿼리를 돌리면, 30개 목록에 대해 **목록 1번 + 답변 수 30번 + 좋아요 수 30번**의 쿼리가 실행된다.

대신 `answerCnt`, `likeCnt` 컬럼을 두고 변경될 때마다 값을 갱신해 두면 목록 조회 한 번으로 끝난다. 이때 고민할 점은 두 가지다.

- 비정규화를 해도 되는가?
- 동시에 갱신될 때 값이 틀어지지 않는가?

### 오프셋 대신 ID 기준으로 조회하기

`limit 10000, 20` 같은 오프셋 방식은 앞의 10,000건을 읽고 버린다. 대신 `where id < 마지막_id` 처럼 **ID를 기준으로 다음 데이터를 가져오면** 읽는 양이 크게 줄어든다.

### 조회 범위를 시간으로 제한하기

시간 컬럼에 인덱스를 두고 최근 데이터만 조회하도록 기능을 설계한다. 최신 데이터 위주라 캐시를 쓰기도 쉽다.

### 전체 개수 세지 않기

목록 쿼리와 별도로 `count` 쿼리를 날려야 하고, 데이터가 많아지면 이 쿼리가 오히려 병목이 된다. 기획과 협의해 **전체 개수를 아예 보여 주지 않는 방향**도 고려할 만하다.

### 오래된 데이터 삭제하거나 분리 보관하기

로그인 내역처럼 계속 쌓이는 데이터는 오래된 것을 지우거나 다른 곳으로 옮긴다.

> DELETE를 해도 DB가 쓰는 디스크 용량은 바로 줄지 않는다. 삭제 표시만 하고 공간은 나중에 재사용하기 때문이다. 추가와 삭제가 반복되면 **단편화**가 생겨 디스크 I/O가 늘고 공간이 낭비된다. 주기적으로 최적화(데이터 재배치)를 해 주자.
{: .prompt-warning }

### DB 장비 확장, 별도 캐시 서버

빠른 해결책이 없다면 일단 DB를 **수직 확장**해 시간을 벌고, 그동안 근본적인 개선책을 찾는 방법도 있다. 주 DB와 복제 DB로 **수평 확장**해 읽기를 나눌 수도 있다. 다만 DB 서버는 비싸니 비용 대비 효과가 확실할 때 하자.

## 알아 두면 좋은 주의 사항

### 쿼리 타임아웃

응답이 느려지면 사용자는 답답해서 재시도를 누른다. 서버는 이전 요청도 처리하지 못하고 있는데 요청이 또 쌓이면서 부하가 폭증한다.

이를 막으려면 **쿼리 실행 시간에 상한을 두자.** 5초로 제한하면 5초 안에 끝나지 않는 쿼리는 에러로 끝나고, 서버는 그만큼 자원을 돌려받는다. 블로그 조회처럼 가벼운 기능은 짧게, 결제처럼 정합성이 중요한 기능은 처리 시간을 고려해 길게 잡는 식으로 기능마다 다르게 정한다.

### 상태를 바꾸는 기능은 복제 DB에서 조회하지 않기

주 DB와 복제 DB가 있다고 모든 SELECT를 복제 DB로 보내면 안 된다.

1. 복제에는 **지연**이 있어서 방금 바꾼 데이터가 아직 반영되지 않았을 수 있다.
2. 복제는 커밋 시점에 일어난다. 주 DB에서 트랜잭션 안에 변경한 뒤 복제 DB에서 조회하면 **변경 전 데이터**를 읽게 된다.

### 배치 쿼리 실행 시간 추적하기

데이터가 쌓이면 배치 쿼리도 서서히 느려진다. 실행 시간을 계속 지켜보고, 느려지면 장비 사양을 올리거나 커버링 인덱스를 쓰거나 데이터를 나눠 처리한다.

### 타입이 다른 컬럼끼리 조인하지 않기

```text
user.userId     → INT
push.receiverId → VARCHAR

INT = VARCHAR → 암묵적 타입 변환 → 인덱스를 못 탈 수 있음 → 데이터가 많을수록 느려짐
```

자주 조인하는 컬럼은 **처음부터 같은 타입으로 설계**하자. 문자열끼리라면 Character Set과 Collation도 맞아야 한다. 인덱스가 있다고 항상 쓰이는 건 아니니, 컬럼에 변환이나 연산이 끼는지 **실행 계획으로 확인**해야 한다.

### 테이블 변경은 신중하게

데이터가 많은 테이블에 `ALTER TABLE`을 날리면 대량 데이터 처리와 잠금이 발생해 서비스가 멈출 수 있다. DB 버전과 DDL 방식, 잠금 여부, 예상 수행 시간을 미리 확인하고, 필요하면 점검 시간을 잡거나 온라인 스키마 변경 도구를 쓰자.

### DB 최대 연결 수

애플리케이션 커넥션 풀만 보면 안 된다.

```text
API 서버 3대 × 풀 30개 = 최대 90 커넥션
API 서버 4대로 확장   = 최대 120 커넥션
DB max_connections = 100 → 새 서버가 커넥션을 못 얻을 수 있다
```

확장할 때는 **인스턴스 수 × 인스턴스당 풀 크기 ≤ DB가 감당할 수 있는 연결 수**인지 함께 확인한다. 단, DB CPU나 쿼리가 이미 병목이라면 `max_connections`부터 늘리는 건 해결책이 아니다. 쿼리 튜닝과 캐시로 부하부터 줄이자.

## 실패와 트랜잭션

트랜잭션의 범위는 **같이 성공하거나 같이 실패해야 하는 작업**을 기준으로 잡는다.

```text
계약 INSERT 성공 ✅ → 회원 상태 UPDATE 실패 ❌
→ 트랜잭션이 없다면 데이터 불일치
```

그렇다고 모든 걸 하나로 묶는 게 정답은 아니다. 회원가입은 성공했는데 환영 메일 발송이 실패했다면, 회원가입까지 롤백해야 할까? 답은 비즈니스 요구사항에 달려 있다.

> 트랜잭션 경계는 기술적으로 묶을 수 있는 범위가 아니라 **비즈니스적으로 함께 성공하거나 실패해야 하는 범위**다. 외부 API나 메일처럼 DB 밖의 작업은 롤백할 수 없으니 별도의 실패 처리 전략이 필요하다.
{: .prompt-tip }

## 정리

DB 성능은 쿼리 한 줄만의 문제가 아니다. **컬럼 타입 → 인덱스 활용 → 커넥션 수 → 트랜잭션 경계 → 스키마 변경**까지 모두 실제 서비스의 성능과 안정성에 영향을 준다.

이 장에서 가장 와닿았던 건 "인덱스가 있다고 항상 타는 건 아니다"라는 부분이다. 직접 성능 실험을 해 보면서 인덱스를 추가했는데도 옵티마이저가 쓰지 않아 실행 계획이 그대로였던 경험이 있다. 결국 실행 계획과 측정으로 확인하는 습관이 가장 중요하다.
